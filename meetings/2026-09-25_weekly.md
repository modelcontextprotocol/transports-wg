# 2026-09-25 MCP: Transport Working Group (Weekly)

## TL;DR
The MCP Transport Working Group reviewed takeaways from MCPCon Europe,
covering pluggable transports, SDK extension points, HTTP over standard I/O,
transport-level tracing headers, caching and tool versioning (PR #45), schema
type constraints (PR #2778), origin validation governance, and an overhauled
protocol release cycle. The group welcomed Shaun Smith as the newly elected
secondary lead maintainer and reviewed a proposed MCP governance update that
would shift the December specification release to March—establishing a recurring
March and September cadence with paired primary and secondary release
managers—and require conformance tests before Specification Enhancement Proposal
(SEP) acceptance. On local transports, attendees leaned toward running HTTP/2
over standard I/O rather than adding LSP-style headers and assigned SDK
prototypes across TypeScript, Rust, Java, and Go ahead of MCPCon North America
in October, pending a formal decision document from Kurtis Van Gent. Key
technical debates centered on balancing pluggable transport abstractions against
ecosystem interoperability concerns, propagating trace context via HTTP headers
so Layer 7 proxies do not parse JSON-RPC bodies, and avoiding breaking changes
when introducing `schema.ts` limits or ETag cache keys. Members will conduct
asynchronous reviews on the open tracing, caching, and type constraint pull
requests ahead of next week's meeting.

### Pluggable Transports, SDK Extensions, and HTTP over Standard I/O
* **Pluggable Transports and Schema Separation:** Recapping discussions from
  MCPCon Europe, Kurtis Van Gent noted ongoing debate among core maintainers
  around pluggable and custom transports—weighing concerns over transport
  proliferation and client-server interoperability against openness to an SEP
  separating the MCP schema from JSON-RPC. Shaun Smith and Kryspin Ziemski
  expressed support for pluggable transports, noting that decoupling server
  logic from the transport layer yields cleaner software architecture without
  posing a material fragmentation risk.
* **Industry Demand and SDK Alignment:** Kurtis Van Gent, Kryspin Ziemski, and
  Luca Chang noted that enterprises and regulated industries are already
  implementing custom transports (such as gRPC, AMQP, or custom signing proxies)
  to meet internal infrastructure requirements. Kryspin suggested aligning on a
  consistent SDK-level transport interface alongside ongoing SDK documentation
  and conformance generation efforts. Kurtis also highlighted a related SEP in
  the SDK Working Group proposing four to five common extension points so
  features like Skills over MCP can be imported as packages rather than
  hardcoded into core SDKs.
* **HTTP/2 over Standard I/O vs. LSP-Style Headers:** Following breakout
  discussions and a Python analysis PR by Kludex, Kurtis Van Gent summarized
  two remaining contenders to replace raw JSON-RPC over standard I/O: adding
  LSP-style headers or adopting HTTP/2 over standard I/O to reuse native HTTP/2
  streaming semantics. Kurtis and Mark Roth favored HTTP/2—relying on existing
  HTTP/2 libraries to mitigate implementation complexity—and Kurtis committed to
  drafting a decision document.
* **Multi-Language Prototyping Assignments:** With Stephen Halter having
  validated a C# prototype and Kludex having analyzed Python, the group
  assigned prototypes targeting MCPCon North America in October to surface
  ecosystem-specific hurdles. Kryspin Ziemski volunteered for TypeScript (noting
  runtime divergences across Node.js, Bun, Cloudflare Workers, and WinterCG) and
  Rust; Luca Chang took Java (noting Spring framework and Netty stack
  integration considerations); and Kurtis Van Gent offered to coordinate with
  the Go SDK team.

### Transport-Level Tracing Headers and Proxy Behavior
* **Moving Trace Context Out of Request Payloads:** Paul Ogilby (Google, Envoy
  maintainer) introduced a pull request proposing transport-level HTTP headers
  for trace context propagation rather than relying on JSON-RPC `_meta` body
  fields, building on prior OpenTelemetry (OTel) metadata discussions. Because
  intermediate Layer 7 proxies routinely mutate tracing headers across hops,
  duplicating trace state in the body causes header-body mismatches, obscures
  proxy hops, or forces proxies to parse full message bodies—an approach most
  proxies currently take.
* **Schema-Transport Separation and Duplication Trade-Offs:** Mark Roth
  strongly opposed requiring proxies to parse message payloads and noted that
  trace propagation belongs in a pluggable transport layer (clarifying in a
  brief tangent that Envoy Mobile, which adds xDS, QUIC, and HTTP/3 support,
  would plug in as an alternate Streamable HTTP client implementation rather
  than a new wire protocol). Paul noted that `_meta` tracing must remain for
  now because raw standard I/O lacks headers. Kurtis Van Gent cautioned against
  carving out ad hoc exceptions to header-body matching rules used by headers
  like `Mcp-Name` and `Mcp-Param-*`, arguing that headers should become the sole
  source of truth once HTTP over standard I/O and schema separation advance.

### Caching, Schema Type Constraints, and Origin Validation
* **Caching Digests and Tool Versioning (PR #45):** Shaun Smith reported major
  updates to PR #45—covering both caching and tool versioning—splitting the
  design into protocol-level digest semantics and an HTTP binding using ETags
  (which requires defining an HTTP GET endpoint for list operations). Open
  questions include whether server instructions belong in or warrant their own
  digest, and whether digests live on cacheable result schemas or in `_meta`.
  Gabriel Zimmerman highlighted server-side combinatorial complexity when
  mapping capability-dependent toolsets (e.g., with and without tasks) to ETag
  cache keys, and Kurtis committed to reviewing Gabriel's capabilities proposal
  to sharpen its problem statement.
* **Schema Type Constraints (PR #2778):** Andreas Schlapbach presented PR #2778
  on the main repository, proposing stricter constraints in `schema.ts` (such
  as non-negative counters and non-empty strings) to standardize SDK validation.
  Mark Roth, Shaun Smith, and Kurtis Van Gent cautioned that strict upper
  bounds—such as string `maxLength` caps, a 10-item limit on icons, or limits
  impacting live commercial servers with 40,000–50,000 tools—risk breaking
  production systems without concrete interoperability failures to justify them.
  Andreas agreed to remove `maxLength` limits and, following suggestions from
  Kurtis and Kryspin Ziemski, consult the SDK, Gateway, and Interceptors
  working groups.
* **Origin Validation and Working Group Governance:** Luc Dao raised an issue
  where current SDK origin validation rules block connections from browser
  extensions that force specific origin headers. Kurtis Van Gent and Shaun Smith
  explained that direct pull requests to the main repository are disabled;
  proposals must originate as SEPs within a working group. Because origin checks
  primarily govern SDK security enforcement, Kurtis advised bringing the
  proposal to the SDK Working Group while offering the Transport Working Group
  repository to stage a draft SEP if needed.

### Protocol Release Cycle Overhaul and Governance
* **Eight-Month Overlapping Release Cadence:** Kurtis Van Gent outlined a
  proposed four-phase, eight-month release cycle with a two-month overlap to
  ship two protocol releases per year: Planning and Prioritization (months 8 to
  6 out, aligning core and working group roadmaps), Core Maintainer SEP Review
  Window (months 6 to 2.5 out), Stabilization (soft freeze at 2.5 months out,
  next-cycle planning kickoff at 2 months out, SDK betas at 6 weeks out, and a
  hard freeze at 4 weeks out permitting only emergency bug fixes during
  production validation), and Release.
* **Formalized Review Queue and Conformance Rigor:** Under the new governance
  model, working group leads must nominate SEPs at least two weeks in advance
  for asynchronous review, formal discussion, and a maintainer vote, with
  roadmap-aligned proposals prioritized in a top tier. Addressing Gabriel
  Zimmerman's question on major versus minor releases, Kurtis explained that
  string-based protocol version negotiation complicates semantic versioning
  (SemVer). Instead, SEPs will require conformance tests prior to acceptance so
  SDKs can implement changes immediately upon merge rather than rushing before
  freezes.
* **Shift to March/September Schedule and Release Managers:** Because an
  October freeze for a December release leaves insufficient runway, maintainers
  plan to shift the next release from December to March and adopt a consistent
  March and September schedule aligned with the North America (April) and
  London (September) conferences—giving HTTP over standard I/O a potential path
  into the upcoming release. The proposal also introduces paired primary and
  secondary release managers, where each cycle the secondary transitions into
  the primary role and a new secondary is onboarded.
