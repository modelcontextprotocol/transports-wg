# 2026-07-31 MCP: Transport Working Group (Weekly)

## TL;DR
The MCP Transport Working Group met to discuss custom transport pluggability,
address inconsistent SDK behavior around subscription streams, and formally vote
on the eight-track roadmap for the next specification release. Kryspin Ziemski
shared exploratory ideas on standardizing an SDK transport interface cut point
before revisiting wire-format coupling, while Shaun Smith highlighted unwanted
open Server-Sent Events (SSE) streams caused by default subscription listener
behavior in SDKs. Participants aligned on drafting a concise Specification
Enhancement Proposal (SEP) for the December release so servers can disable
`subscriptions/listen` and clients avoid opening streams when relevant
capabilities are absent, though Mark Roth cautioned against relying solely on
cached capabilities in horizontally scaled deployments. Mark then walked through
all eight roadmap tracks—covering tool versioning via ETag-like identifiers,
pluggable transports, error standardization, standard I/O strategy, streaming,
internationalization, tool capabilities, and maintaining the status quo on
sessions—noting that details like Gabriel Zimmerman's tool migration feedback
belong in SEP drafting. Finally, the group unanimously approved the roadmap 7 to
0 for submission to the core contributors and canceled next week's meeting while
awaiting their review.

## Detailed Summary

### Pluggable Transports Architecture
* **Two-Step SDK Refactoring Path:** Kryspin Ziemski shared findings from
  reviewing past and current custom transport implementations, noting that MCP
  Apps already utilizes a message transport abstraction. He proposed tackling
  pluggability in two phases: first retaining JSON-RPC as a requirement while
  establishing a standard transport interface across every SDK as a clean cut
  point separating client and server logic from transport mechanics, and second
  evaluating whether custom transports could support alternative wire encodings.
* **Cross-SDK Interfaces and Wire Decoupling:** Kryspin noted that the
  TypeScript SDK already exposes a transport interface, Python v2 separates the
  server from the server runner, and other SDKs should provide an equivalent
  architectural boundary before considering optional wire-format decoupling.
  Mark Roth noted the idea was interesting and suggested continuing the
  discussion offline.

### Subscription Listen Behavior and Capabilities Caching
* **Unwanted Open SSE Streams in SDKs:** Shaun Smith raised a specification and
  SDK consistency gap for servers that do not emit subscriptions, sharing a
  GitHub repository report comparing the Go, TypeScript, and Python SDKs. In
  particular, the TypeScript SDK enables the `subscriptions/listen` endpoint by
  default and offers no default mechanism to close connections, leaving idle
  Server-Sent Events (SSE) streams open and causing unnecessary network traffic.
  While the TypeScript SDK provides a maximum-subscribers knob, setting it to
  zero has different semantics and causes clients to repeatedly retry calling
  the endpoint.
* **C# SDK Comparison and Scope Clarification:** Stephen Halter noted that the
  C# SDK on the latest protocol version closes `subscriptions/listen` by
  default—with an open pull request for manual handling of resource subscription
  notifications—to avoid keeping idle SSE streams open. Gabriel Zimmerman asked
  whether `subscriptions/listen` affects `tools/call` or should tie into
  required capability negotiation to prevent server errors; Mark Roth and
  Stephen Halter clarified that the endpoint only carries list-change
  notifications and resource subscriptions, whereas individual tool results use
  tasks.
* **December SEP for Disabling Subscriptions:** Mark Roth, Shaun Smith, and
  Stephen Halter agreed to address this gap with a small SEP for the December
  release rather than creating a major roadmap track. Mark proposed two rules:
  SDKs should expose a configuration knob to leave `subscriptions/listen`
  unimplemented on the wire, and clients `SHOULD NOT` attempt to open the stream
  when a server advertises no list-notification or subscription capabilities
  during discovery. Mark advised Shaun to draft the SEP and sync with Kurtis Van
  Gent.
* **Capabilities Caching and Lifetime Risks:** Mark Roth highlighted a broader
  architectural limitation with relying on capabilities, pointing out that MCP
  has not defined Time-To-Live (TTL) or cache-lifetime semantics for server
  capabilities. Because rolling upgrades on horizontally scaled services can
  change capabilities mid-flight and invalidate cached assumptions, Mark
  expressed a preference for a "try-and-see" approach where clients invoke a
  method and handle an unimplemented error cleanly.

### Next-Release Roadmap Review
* **Track 1 — Tool Versioning:** Mark Roth walked through the eight-track
  roadmap compiled by Kurtis Van Gent, starting with an ETag-like versioning
  mechanism for individual tool definitions so servers can detect outdated
  client calls and prompt a tool-list refresh and retry. Gabriel Zimmerman
  suggested supporting a graceful server-side migration path (such as hooks
  translating renamed parameters) rather than always throwing an error; Mark
  noted backward-compatible server translations avoid the issue naturally and
  agreed such details belong in the SEP phase rather than the roadmap.
* **Track 2 — Pluggable Transports:** Described by Mark Roth from his
  perspective as the largest unfinished item from the July specification and an
  important enabler for gRPC, this track focuses on ensuring all SDKs provide a
  clean, consistent API for plugging in custom transports.
* **Track 3 — Error Standardization:** Newly added by Kurtis Van Gent after the
  previous meeting, this track builds on the prior specification's error ranges
  to standardize specific error codes and define how HTTP status codes and
  JSON-RPC errors interact.
* **Track 4 — Standard I/O (`stdio`) Transport:** This track addresses the
  long-term architectural strategy for the `stdio` transport, which Mark Roth
  expected to overlap substantially with the pluggable transports work in Track
  2.
* **Tracks 5 to 8 — Streaming, Internationalization, Capabilities, and Status
  Quo:** Mark summarized the final four tracks: Track 5 covers streaming tool
  call results and interactions with tasks (championed by Shaun Smith); Track 6
  defines what can and cannot be internationalized alongside caching impacts;
  Track 7 covers tool capability requirements (championed by Gabriel Zimmerman,
  who re-added wording suggestions on the roadmap draft); and Track 8 explicitly
  maintains the status quo on sessions until demonstrable use cases emerge that
  existing mechanisms cannot solve. Mark also noted to Stephen Halter that
  inserting Error Standardization at position three suggests an implied priority
  order across the tracks.

### Roadmap Vote and Meeting Schedule
* **Directional Scope of Vote:** Clarifying expectations for Gabriel Zimmerman
  and Stephen Halter, Mark Roth explained that voting approves presenting the
  high-level roadmap tracks to the core contributors for sign-off before
  investing six months in detailed engineering. Once approved, track drivers
  will draft individual SEPs and refine specifics using the same process as the
  July specification cycle.
* **Unanimous 7–0 Approval:** After walking through all eight tracks so all
  attendees had full context, Mark Roth called a show-of-hands vote. The roadmap
  passed unanimously, 7 to 0, with Mark noting that Kurtis Van Gent will likely
  incorporate pending wording comments into the pull request before taking the
  document to the core contributors.
* **Schedule Adjustment:** With Kurtis Van Gent unavailable next Friday and core
  contributor review of the roadmap underway over the next couple of weeks,
  attendees agreed to cancel next week's meeting and reconvene in two weeks.
