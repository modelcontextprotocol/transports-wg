# 2026-09-04 MCP: Transport Working Group (Weekly)

## TL;DR
The MCP Transport Working Group reviewed pull requests on subscribe behavior
and ETag caching, discussed core maintainer feedback on the Content Negotiation
Specification Enhancement Proposal (SEP), evaluated a .NET prototype for HTTP/2
over standard I/O, and debated Gabriel Zimmerman's updated Required Capabilities
SEP. Stephen Halter demonstrated that HTTP/2 over standard I/O works end-to-end
with OAuth over TCP back-channels, prompting alignment around exploring an
explicit "Standard I/O v2" transport advertised out-of-band via server cards
to avoid legacy negotiation failures. The majority of the meeting centered on
client-side versus server-side tool filtering: Gabriel Zimmerman and Mark Roth
advocated for client-side `requiredCapabilities` metadata to preserve
statelessness and avoid combinatorial $O(N^2)$ proxy cache explosions, while
Kurtis Van Gent warned of a client-adoption chicken-and-egg problem that could
degrade user experience if naive clients ignore filtering hints. Rather than
advancing the Required Capabilities SEP immediately, the group agreed to expand
its problem statement around caching scopes and MCP proxy pain points ahead of
discussions at MCPCon Europe. Finally, the team canceled the next two weekly
meetings due to conference schedules, shifting coordination to Discord during
the hiatus.

### HTTP/2 over Standard I/O Prototyping
* **.NET Prototype and Loopback Trade-offs:** Stephen Halter demonstrated an
  end-to-end .NET prototype running HTTP/2 over standard I/O (`stdio`) by
  replacing underlying sockets in .NET's HTTP handler on both client and
  server. While straightforward in .NET, Stephen questioned whether other
  language runtimes expose comparably clean extension points. He contrasted
  `stdio` with local loopback TCP sockets: although loopback sockets allow
  parallel HTTP/1.1 connections, they introduce DNS rebinding risks,
  cross-process access exposure, and machine-level security concerns.
* **Protocol Negotiation and Standard I/O v2:** Stephen explained that while an
  HTTP/2 server can sniff the cleartext `h2c` connection preface and fall back
  to legacy `stdio`, clients sending initial HTTP/2 frames will break existing
  `stdio` servers and require an error- or timeout-driven process restart.
  Kurtis Van Gent proposed defining a distinct "Standard I/O v2" transport
  signaled out-of-band via server cards (similar to `.well-known` metadata),
  which Stephen agreed would cleanly avoid in-band probing failures.
* **Header Deduplication, Paths, and OAuth Compatibility:** Prototyping surfaced
  several standardization questions, including deduplicating JSON-RPC `_meta`
  fields and error codes from HTTP headers and status codes, leveraging native
  HTTP caching semantics, and switching from Stephen's temporary `/mcp` test
  path to the root path (`/`). Stephen confirmed that OAuth works end-to-end
  with HTTP/2 over `stdio` as long as authorization server back-channel calls
  and browser redirects use normal TCP/HTTP sockets, though the spec must
  standardize the OAuth resource indicator in the `Host` header. Stephen agreed
  to write a concise brief covering localhost port trade-offs, negotiation,
  `.well-known` server cards, and OAuth details before Tuesday (Amsterdam time).

### Required Capabilities SEP: Client-Side vs. Server-Side Filtering
* **Client-Side Filtering via Tool Metadata:** Gabriel Zimmerman presented an
  updated Required Capabilities SEP that opts for client-side filtering to align
  with TTL caching and upcoming tool versioning. The proposal adds a lightweight
  `requiredCapabilities` hint inside a tool's `_meta` envelope when a tool has a
  hard cross-capability dependency—such as `tasks` or `elicitation`—with no
  fallback mode. Clients can filter out unsupported tools before passing them to
  the LLM or display clear diagnostics in UIs and the MCP Inspector instead of
  failing at execution time.
* **MCP Proxy Scaling and Statelessness:** Kurtis Van Gent questioned why ETags
  could not address capability mismatches and noted that server-side filtering
  is common today. Gabriel clarified that client capabilities are generally
  static rather than changing mid-workflow, and Mark Roth strongly opposed
  server-side capability filtering because it creates an $O(N^2)$ cache-key
  explosion for MCP proxies aggregating multiple backend servers across diverse
  clients. Mark and Gabriel added that after the July statelessness changes
  removed `initialize` in favor of per-request capabilities, server-side
  filtering would either reintroduce implicit state or require `tools/list`
  requests to declare capabilities meant for secondary `tools/call` operations.
  Shaun Smith viewed the field as a simple static tool annotation, and Stephen
  Halter supported it, noting the C# SDK filters on auth metadata when present
  but currently returns unfiltered tool lists for capabilities and fails at call
  time.
* **Client Adoption Inertia and Enforcement Risks:** Kurtis Van Gent raised two
  concerns: server authors may resist abandoning server-side filtering, and
  optional client features often see uneven adoption—noting varying host support
  across `tasks`, `elicitation`, and tool search. Kurtis warned of a
  chicken-and-egg penalty where compliant servers expose unfiltered tool lists
  that naive clients pass directly into LLM context windows. When Mark Roth
  suggested mandating client filtering in SDKs and argued protocols should leave
  user experience to clients, Kurtis noted that SDK mandates can be difficult to
  enforce in practice, pointing to recent developer pushback that led to making
  TTL fields optional in SDKs.

### Cache Scoping and Problem Statement Refinement
* **Public/Private Cache Scopes and Auth Filtering:** Kurtis Van Gent pointed
  out that production servers already vary `tools/list` by user authentication.
  While Stephen Halter viewed user auth as distinct from capabilities, Mark Roth
  argued that any server-side filtering impedes proxy caching. Shaun Smith and
  Kurtis noted that the specification already includes HTTP-style `public` and
  `private` cache scope flags alongside TTLs. After reviewing the spec, Mark
  suggested that since `private` cache scopes already support dynamic
  server-side filtering when needed, Gabriel's SEP offers a clean paved path for
  servers that want `public`, proxy-cacheable tool lists. Kurtis and Gabriel
  also discussed whether explicit cache-invalidation criteria, client-scoped
  cache keys, or ETags could model server-side alternatives.
* **Sharpening the SEP Problem Statement:** Kurtis noted that the current SEP
  draft focuses on the `tools/list`-to-`tools/call` differential rather than MCP
  proxy caching, emphasizing the value of concrete operational examples from
  proxy and gateway builders alongside abstract caching arguments. While Shaun
  Smith and Gabriel emphasized preserving the core goal of preventing runtime
  capability failures and opaque black-box imports, the group agreed not to
  advance the SEP yet: Gabriel will expand the problem statement and caching
  alternatives, and Kurtis will gather early core maintainer feedback at MCPCon
  Europe and document his transition concerns.
