# 2026-10-16 MCP: Transport Working Group (Weekly)

## TL;DR
The MCP Transport Working Group met to evaluate protocol negotiation for HTTP
over standard I/O (#61), review the Specification Enhancement Proposal (SEP)
separating the protocol data model from JSON-RPC (#58), and discuss streaming
authorization and subscription lifecycle management (#62, #63, #64). For HTTP
over standard I/O, the group weighed startup negotiation via environment
variables (Option 1) against introducing a separate `standard I/O v2` transport
(Option 2), leaning toward Option 1 in a 6-vote poll pending a C# prototype by
Stephen Halter to validate bidirectional handshake mechanics. On data model
separation, Kurtis Van Gent presented a transport-neutral schema that eliminates
header-and-body duplication such as trace context mismatches while retaining
JSON-RPC on the wire for Streamable HTTP and standard I/O, adopting Stefan
Moser's suggestion to add an optional top-level `name` field. With the
primitive versioning item (#57) deferred, Ramjot Singh introduced proposals
informed by production experience with large-scale subscription APIs to handle
OAuth token expiration, stream closure, and in-band reauthorization on
long-lived subscription streams. Participants debated proactive
`authorizedUntil` rollover versus best-effort notification semantics and
connection control codes, aligning to split the broad lifecycle proposals into
smaller, single-problem SEPs and canceling next week's October 23 meeting due
to AGNTCon presentations.

## Detailed Summary

### HTTP over Standard I/O Negotiation (#61)
* **Startup Negotiation vs. Clean Transport Break:** Kurtis Van Gent framed two
  approaches for transitioning local servers to HTTP over standard I/O, noting
  that unlike existing discovery-message fallbacks, HTTP requires speaking
  `HTTP/1.1` and `HTTP/2` upfront. Option 1 negotiates at startup via a
  client-set environment variable and server acknowledgment with fallback to
  legacy standard I/O—risking process restarts and cascading negotiations—while
  Option 2 defines an explicit `standard I/O v2` transport for a clean, safer
  break at the cost of manual user configuration updates.
* **SDK Byte-Sniffing Feasibility and Ecosystem Stickiness:** Mark Roth noted
  that Option 2 would prolong deprecating legacy standard I/O and emphasized
  verifying whether SDKs across languages can negotiate on raw file descriptors
  before handing streams to an HTTP library. Stephen Halter reported that his C#
  SDK prototype can sniff initial `HTTP/2` cleartext (`h2c`) bytes before
  passing the stream to the HTTP stack, though it is inelegant and potentially
  difficult in other languages; he suggested standardizing any `v2` environment
  variable for diagnostics, while noting that server stickiness favors
  spec-level negotiation so clients do not invent ad-hoc restart loops.
* **Proxy Adapter Brainstorm and Clean-Break Arguments:** Mark Roth brainstormed
  placing a language-agnostic local proxy adapter between client and server for
  a bounded deprecation window (e.g., two protocol versions) so clients always
  speak `HTTP/2` while the proxy sniffs and translates legacy standard I/O
  servers. Kurtis Van Gent noted Shaun Smith thought an adapter was feasible,
  but Kurtis and Stephen Halter argued it adds proxy overhead and undermines
  retiring legacy standard I/O design constraints. Conversely, Ramjot Singh
  favored Option 2 to avoid supporting legacy startup behavior indefinitely, and
  Kryspin Ziemski suggested a no-op `v1` legacy environment variable to nudge
  migration—which Kurtis and Stephen cautioned would add user config friction
  and risk breaking host setups.
* **Bidirectional Handshake Mechanics and Prototyping Plan:** With feedback from
  Tuesday's bi-weekly SDK maintainer meeting still pending, Kurtis proposed—and
  Mark Roth supported—validating Option 1 with a prototype first. Kurtis and
  Stephen Halter identified the core challenge:
  while an environment variable cleanly signals client support to a subprocess,
  HTTP expects the client to transmit first, requiring the server to emit an
  initial parsable JSON acknowledgment before HTTP traffic begins without
  fragile startup timeouts (with Mark also suggesting an `HTTP/1.1` probe
  request to a new path). Stephen volunteered to extend his C# prototype with
  the environment variable and JSON sentinel message.

### Separating the Protocol Data Model from JSON-RPC (#58)
* **Transport-Neutral Schema and Motivation:** Kurtis Van Gent presented the
  draft SEP decoupling MCP's protocol data model from its transport wire
  representation. Tying the schema directly to JSON-RPC currently forces field
  duplication across headers and message bodies—most notably trace context,
  where HTTP header mutations by non-MCP-aware proxies conflict with body
  fields. The proposed top-level interface surfaces `protocolVersion`, `method`,
  `metadata` (mapping `_meta`), and `payload` (mapping JSON-RPC `params`),
  paired with explicit rules for translating the data model onto transport wire
  formats.
* **Three-Stage Rollout and JSON-RPC Wire Compatibility:** Addressing Stefan
  Moser's question on long-term direction, Kurtis explained that core
  maintainers previously opposed replacing JSON-RPC on Streamable HTTP (such as
  moving to REST) to avoid disruptive churn similar to the stateless transition.
  Streamable HTTP and standard I/O will therefore continue using JSON-RPC on the
  wire, and Kryspin Ziemski suggested making this continuity explicit in the
  spec text to clarify backward-compatibility expectations. Kurtis outlined the
  planned three-SEP sequence: (1) separating the data model from transport
  representations, (2) decoupling JSON-RPC from custom transport requirements,
  and (3) proposing a pluggable transport interface for Tier-1 SDKs.
* **SDK Boundaries and Optional Top-Level `name` Field:** Stephen Halter
  endorsed eliminating header-and-body trace ID duplication while questioning
  impacts on internal SDK APIs; Kurtis confirmed the SEP does not dictate SDK
  API shapes. Stefan Moser proposed lifting `name` (used in `params.name` for
  `tools/call` and applicable resource or prompt operations) to the top-level
  interface so transports can route or populate headers directly; after
  confirming with Stephen that `name` only applies to certain methods, Kurtis
  agreed without objection to add `name` as an optional top-level field.
* **Complementary Scope and Cross-Transport Authorization:** Mark Roth strongly
  supported the abstraction (including for transports like gRPC and AMQP) and
  emphasized clearly distinguishing how HTTP over standard I/O (focused on
  streaming and metadata parity) and data model separation (preventing breaking
  schema changes) complement rather than replace one another. Answering Andrey
  Velichkevich, Kurtis clarified that authorization currently applies only to
  Streamable HTTP and remains out of scope here to keep the SEP focused, though
  the neutral data model facilitates future cross-transport authorization
  standardization.

### Streaming Authorization and Subscription Lifecycle (#62, #63, #64)
* **OAuth Token Expiration on Long-Lived Subscriptions:** Ramjot Singh presented
  issue #62 and PR #63 addressing long-lived Server-Sent Events (SSE)
  subscription streams
  that outlive the initial OAuth token (commonly 1 hour). Today, servers either
  allow unauthorized streams to persist indefinitely or drop connections
  abruptly without explanation, forcing blind retries since Identity Providers
  (IdPs) discourage clients from inspecting tokens. Ramjot proposed requiring
  per-notification server validity checks, explicit authorization-ended closure
  messages, and an `authorizedUntil` parameter on subscription acknowledgements
  so clients can proactively open a fresh stream before token expiry.
* **`authorizedUntil` Rollover vs. Transport Scope and Multiplexing:** Kurtis
  Van Gent questioned whether `authorizedUntil` solves the root issue since
  mid-stream IdP token revocations or permission changes can still terminate
  streams early, suggesting SSE resumability (via last-seen event IDs) instead,
  while Ramjot noted routine expiry is far more frequent than revocation.
  Answering Stefan Moser, Ramjot confirmed the proposal targets remote
  transports—primarily Streamable HTTP—and Stefan stressed keeping authorization
  transport-scoped rather than embedded in generic payloads. Matt Pavlovich,
  Stephen Halter, Kurtis, and Ramjot also clarified that unlike standard I/O
  (which multiplexes subscriptions via subscription IDs), Streamable HTTP binds
  each subscription listen stream to a single HTTP request/SSE connection,
  making connection closure on auth expiry clean without stateful session
  multiplexing.
* **Best-Effort Notification Semantics and Connection Control:** On the risk of
  losing events when closing expired streams, Mark Roth emphasized—and Kurtis
  agreed—that subscription notification streams were designed from the start as
  optional, best-effort optimizations that may drop at any time rather than
  guaranteed delivery channels, meaning missed events during reconnection are
  working as intended. Matt Pavlovich suggested folding stream termination into
  a general connection-control packet mechanism with reason codes (e.g.,
  authorization expiry, server shutdown, or host migration) to instruct clients
  how to reconnect.
* **Lifecycle Extensions and Problem Decomposition:** Ramjot introduced
  follow-up PR #64—drawn from production experience with large-scale
  subscription APIs—covering in-band token refresh notifications
  (`reauthorization required` via `sub/update`), missed-notification alerts
  after stream pauses or server issues, and reduced-access notices when
  permissions are revoked for a subset of resources in a multi-resource
  subscription. Kurtis advised decoupling these intertwined concerns (such as
  auth enforcement versus notification resumability) into smaller,
  single-problem proposals backed by concrete production use cases, and Ramjot
  agreed.

### Poll Results and Meeting Schedule
* **Straw Poll Outcomes:** At the close of the meeting, Kurtis Van Gent reported
  6 votes on the HTTP over standard I/O negotiation poll leaning toward Option 1
  (startup protocol negotiation) and 3 votes in favor of separating the protocol
  data model from transport representation, encouraging remaining attendees to
  submit their votes.
* **Upcoming Meeting Cancellation and Availability:** Kurtis canceled next
  week's October 23 meeting because both he and Shaun Smith will be away
  presenting at AGNTCon. The working group will reconvene on October 30, with
  Stephen Halter planning to share updates on his negotiation prototype in
