# 2026-11-06 MCP: Transport Working Group (Weekly)

## TL;DR
The MCP Transport Working Group reviewed updates to tool primitive versioning,
HTTP over standard I/O (`stdio`) negotiation, the promotion of pluggable
transports to SEP-3498, internationalization reviewer feedback, and subscription
stream error handling. The group aligned on merging the HTTP over `stdio`
negotiation design to begin multi-SDK prototyping, scheduling SEP-3498 for core
maintainer review, keeping programmatic fields untranslated while leaving
model-facing translation optional (`MAY`), and generalizing stream termination
error signaling beyond authorization. Key technical debates centered on
list-level versus per-primitive version digests for large tool and resource
sets, HTTP/1.1 upgrade semantics versus TLS ALPN, target audience boundaries
across programmatic, model-facing, and user-facing fields, and extensible
end-of-stream error reporting for `subscriptions/listen` and future streaming
extensions. With core maintainer meetings slowing for upcoming holidays, the
group plans to vote on tool primitive versioning scope next week while advancing
SDK prototypes, internationalization conformance prerequisites, and revised
stream error proposals asynchronously.

## Detailed Summary

### Tool Primitive Versioning Scope and Groupings
* **SEP Revisions and List-Result Scope:** Shaun Smith reported incorporating
  prior feedback into the tool primitive versioning Specification Enhancement
  Proposal (SEP), adding concrete scenarios, clarifying that clients send all
  primitive or tag IDs on every request, and adding rolling-deployment warnings
  from Gabriel Zimmerman. Shaun noted that scoping version tags to `tools/list`
  results remains defensible in the SEP rationale because list results contain
  the actual definitions, whereas adding per-tool descriptors and digests would
  cause broad ripple effects across the protocol.
* **List-Level vs. Per-Primitive Digests:** Kurtis Van Gent questioned whether
  list-level scope suffices given that skills include per-file digests, raising
  network efficiency concerns as MCP scales to large tool sets and potentially
  thousands or millions of resources where a single item update invalidates the
  entire list—including undiscovered tools. Sam Morrow defended list-level
  hashes as an opportunistic, optimistic concurrency and caching model that
  avoids transmitting millions of individual hashes while casually warning
  clients of cache staleness (including additions or removals) without blocking
  active calls. Gabriel Zimmerman noted that clients can resolve specific diffs
  locally or via a future change-list API call. Kurtis will review the SEP,
  potentially draft a pros-and-cons decision document, and hold a vote next
  week.
* **Stateless Tool Groupings Interaction:** Sam Morrow asked whether clients
  using progressive discovery groupings could send enabled-group metadata on
  every request so servers could return an opaque hash scoped only to enabled
  groups. Kurtis Van Gent clarified that groupings are intentionally stateless—
  servers do not track which groups a client has discovered, and clients query
  groups directly by name—and suggested raising this interaction with the
  Progressive Disclosure Working Group.

### HTTP over Standard I/O Negotiation and Pluggable Transports
* **Negotiation Design and Timeout Handling:** Kurtis Van Gent presented a draft
  negotiation flow for HTTP over standard I/O (`stdio`) where HTTP/2-only
  servers send an HTTP/2 upgrade notice immediately, while multi-version servers
  layer an HTTP/2 upgrade onto the existing `server/discover` notification
  handshake. Luca Chang confirmed that his prior concern about slow-starting
  servers and late `server/discover` responses causing silent fallbacks was
  resolved in the latest revision. Kurtis noted that SDKs currently handle
  discovery fallbacks inconsistently (for example, Python skips server process
  restarts while Go may restart).
* **HTTP/1.1 Upgrade vs. ALPN Nuance:** Stephen Halter noted that while the
  draft models its handshake after an HTTP/1.1-to-HTTP/2 upgrade, modern HTTP/2
  implementations deprecated cleartext HTTP/1.1 upgrades (still used for
  WebSockets) in favor of TLS Application-Layer Protocol Negotiation (ALPN) or
  prior-knowledge preface sniffing, clarifying that Go negotiates HTTP/2 via
  TLS ALPN rather than cleartext upgrades. Kurtis noted manual upgrade rules in
  `nginx` configurations and asked whether any historical HTTP/1.1 upgrade flaws
  affect the `stdio` design; Stephen agreed to investigate further and comment
  on the pull request.
* **Multi-SDK Prototyping:** Before promoting HTTP over `stdio` to an official
  SEP, Kurtis proposed merging the negotiation design (barring objections) and
  validating feasibility across SDKs to secure SDK maintainer buy-in. Stephen
  Halter volunteered to continue his prototype, Kryspin Ziemski reported
  building TypeScript workflow test cases, and Debanshu Das volunteered to build
  a Go SDK prototype PR alongside contributors testing feasibility in MCP
  Toolbox.
* **Pluggable Transports Promoted to SEP-3498:** Kurtis Van Gent announced that
  the transport separation data model proposal previously approved by the
  working group has been promoted to official SEP-3498 in the core
  `modelcontextprotocol` repository. After confirming the repository location
  for Matt Pavlovich, Kurtis stated he will schedule SEP-3498 for review with
  the core maintainers.

### Internationalization and Field Audience Definitions
* **Reviewer Feedback and Target Audiences:** Sam Morrow reported that the
  internationalization (content negotiation) SEP was approved with core
  maintainer comments that must be addressed alongside a reference
  implementation and conformance tests before merging. Addressing Yuki Suzuki's
  observation that `description` is used for both users and models, Shaun Smith
  advocated strictly keeping `description` model-facing and `title`
  user-facing. Luca Chang and Sam Morrow noted that `title` carries tight
  character constraints akin to a readable tool name rather than a long-form
  human description, while reviewer feedback suggested explicitly labeling
  human-facing versus model-facing fields across the specification.
* **Optional Model-Facing Translation (`MAY`):** Sam Morrow argued against
  reviewer suggestions to mandate or prohibit translating `description` fields,
  citing regional deployments (such as multilingual healthcare MCP servers in
  Africa paired with regionally tuned models) where server authors should decide
  based on local context and evaluations. Shaun Smith agreed that server authors
  must control model-bound tokens based on their own testing heuristics—similar
  to personalized skills—rather than forcing costly re-evaluations (`evals`) via
  spec mandates, and Luca Chang agreed that translating descriptions makes
  `evals` harder.
* **Programmatic Fields and Error Messages:** Responding to Matt Pavlovich on
  deterministic machine handling in multilingual servers, Sam Morrow agreed that
  error text should remain untranslated to avoid breaking string-matching
  consumers. Mark Roth shared gRPC's stance that status codes are strictly for
  machines while error messages are for humans without stability guarantees,
  which Sam asked him to add to the PR thread. Kurtis Van Gent synthesized a
  three-audience model: programmatic fields (such as harness-bound tool names
  and JSON-RPC error messages) must not be translated, whereas model-facing and
  user-facing fields may be translated as needed. Mark Roth emphasized
  clarifying protocol layering as natural-language models blur traditional
  machine-human boundaries, and Sam agreed to clarify field audiences either
  inline in the current SEP or in a standalone SEP depending on scope.

### Subscription Token Expiry and Generic Stream Error Signaling
* **PR #67 Revisions on Stream Expiry:** Ramjot Singh presented updates to
  PR #67 (part of splitting his auth lifecycle work into smaller
  proposals, deferring mid-stream lifecycle notifications to a later proposal)
  addressing `subscriptions/listen` streams that outlive access tokens. Based on
  prior feedback not to overburden servers that only check auth at stream
  establishment, Ramjot softened `MUST`/`MUST NOT` enforcement to
  `SHOULD`/`SHOULD NOT` recommendations and focused on structured pre-closure
  error reporting (such as token expiration, revocation, or insufficient scope)
  so clients can refresh tokens via the IdP or re-prompt consent. Shaun Smith
  confirmed this aligned with last week's guidance.
* **Existing `result` Type Constraints:** Kurtis Van Gent asked why
  `subscriptions/listen`—which currently signals graceful closure via `result`
  type `complete`—could not return a `result` type like `authorization_ended`.
  Ramjot explained that current spec assumptions lead clients to interpret
  unrecognized `result` types as normal operational completion rather than
  recoverable errors.
* **Generalizing Stream Error Signaling:** Matt Pavlovich suggested broadening
  the design to cover connection and stream control events like rate limiting
  and redirects. Mark Roth agreed that although `subscriptions/listen` is the
  main intended stream today (noting legacy SSE progress streams on tool
  responses were never formally removed), MCP should introduce a generic
  end-of-stream error building block for future streaming methods. Kurtis Van
  Gent noted that the upcoming `events` extension may also use optional streams
  and benefit from termination signals like server shutdown reconnects. Ramjot
  agreed to review the `events` extension, propose a generic stream error
  mechanism defining client fallback behavior for unknown error codes, and
  revise PR #67 for async review.
