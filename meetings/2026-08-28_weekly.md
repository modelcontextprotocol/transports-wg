# 2026-08-28 MCP: Transport Working Group (Weekly)

## TL;DR
The MCP Transport Working Group reviewed proposal statuses ahead of MCPCon
Europe, refined the ETag-based tool digest proposal into "primitive versioning,"
scoped a prototype for running HTTP over standard I/O, and aligned on expanding
a rate-limiting proposal into comprehensive HTTP error code standardization. The
group agreed that primitive versioning should be an optional field rather than a
negotiated capability, and converged on HTTP/2 as a practical requirement for
multiplexing parallel requests over standard I/O pipes despite historical
concerns about SDK-less implementation complexity. Guest contributor Stephen
Tyree presented a dual-layer rate-limiting design spanning HTTP headers and
JSON-RPC errors, which Kurtis Van Gent proposed broadening to map all HTTP
status codes consistently across SDKs. Meanwhile, the group shelved an idea for
an external wiki-style schema vocabulary in favor of keeping core error mappings
strictly within the formal specification.

## Detailed Summary

* **Roadmap and Pluggable Transports:** Kurtis Van Gent reported that the
  working group roadmap was cleaned up and merged following last week's review.
  Mark Roth noted he is continuing outreach to external gRPC users and plans to
  gather feedback during next week's gRPConf. Kurtis announced plans to draft a
  document next week fleshing out the argument for pluggable transports and
  gather stakeholder feedback ahead of the final decision at MCPCon Europe.
* **ETag Proposal Renamed to Primitive Versioning:** Shaun Smith checked on
  moving the ETag digest proposal to the core maintainers. Kurtis offered to
  sponsor the Specification Enhancement Proposal (SEP) in the review queue once
  finalized and suggested renaming it from "deterministic per-primitive digest"
  to "primitive versioning." Shaun agreed and recommended adding a one-paragraph
  TL;DR clarifying the core mechanism: calling a changed tool can return an
  error prompting a refresh. Kurtis and Shaun also aligned that server
  enforcement should be optional—allowing servers to either execute the older
  tool version or return an error requesting a new tools list—and that explicit
  capability advertisement should be dropped in favor of an optional field.
* **Per-Request User Language Proposal:** Kurtis and Shaun confirmed that the
  per-request user language (internationalization) proposal has already been
  opened in the main repository. Viewing it as a transport-specific feature,
  Shaun expressed support, and Kurtis committed to placing it into the SEP
  review queue.
* **VS Code Protocol Adoption:** Shaun Smith asked about VS Code's timeline for
  adopting the latest MCP protocol release. Stephen Halter offered to check with
  the VS Code team regarding their adoption roadmap.

### HTTP over Standard I/O: Prototyping and Design Questions
* **Avoiding the Standard I/O Tax:** Kurtis Van Gent reiterated that the goal of
  running HTTP over standard I/O (`stdio`) is to preserve frictionless local
  command execution (such as `npx` workflows) without imposing a "tax" on remote
  protocol development, where HTTP-native features are frequently blocked
  because legacy `stdio` cannot support them.
* **C# (.NET) Prototyping Plan:** Stephen Halter volunteered to build an initial
  prototype in C# (.NET), explaining that .NET's in-process client and server
  abstractions can readily run over arbitrary streams or pipes, though
  ergonomics will vary across languages. He noted the prototype will also help
  clarify how messages split between `stdio` streams and network requests.
* **Negotiation and Metadata Deduplication:** Kurtis outlined key open questions
  for the prototype to surface before core maintainer day: defining a clean
  negotiation strategy (favoring a distinct `stdio` v2 transport rather than
  messy in-band negotiation on legacy `stdio`), identifying limitations when no
  base URL exists (such as `.well-known` discovery paths), normalizing required
  headers like `Host`, and deduplicating metadata between JSON-RPC payloads and
  HTTP headers—specifically whether fields like protocol version should remain
  in `_meta` or move solely to HTTP headers as the single source of truth.

### HTTP/2 Requirements and Local Transport Trade-offs
* **SDK-less Simplicity vs. Multiplexing:** Mark Roth noted past core maintainer
  concerns about keeping MCP simple enough to implement without an SDK—a bar
  that would rule out HTTP/2 and HTTP/3—and advised gauging core maintainer
  buy-in on HTTP/2 early. Kurtis and Stephen Halter argued that HTTP/2 is
  practically required to multiplex parallel calls over a single `stdio` pipe
  without spawning multiple processes.
* **Why HTTP/1.1 and HTTP/3 Do Not Fit:** While Stephen Tyree suggested
  supporting full HTTP version negotiation over `stdio` so standard RFCs apply
  cleanly, Mark Roth and Stephen Halter explained why neither HTTP/1.1 nor
  HTTP/3 is viable. HTTP/1.1 cannot multiplex concurrent requests over a single
  stream, and typical version negotiation relies on TLS ALPN. Conversely, HTTP/3
  runs over QUIC/UDP rather than a byte stream and mandates TLS certificates,
  complicating local development (for example, ASP.NET Core's Kestrel disables
  HTTP/3 by default because browsers reject self-signed certificates without a
  trusted CA). Mark confirmed that gRPC already runs HTTP/2 cleanly over pipes
  and Unix domain sockets and has no plans to move off HTTP/2 despite browser
  migration toward HTTP/3.
* **Localhost TCP and Unix Socket Alternatives:** Stephen Tyree and Kryspin
  Ziemski asked whether introducing a breaking `stdio` v2 transport warranted
  switching to localhost TCP or IPC mechanisms like Unix domain sockets. Kurtis
  explained that spinning up ephemeral localhost ports was previously rejected
  due to operational complexity and DNS rebinding security risks; while Mark
  Roth noted Unix domain sockets can carry datagrams (`SOCK_DGRAM`), Kurtis,
  Stephen Tyree, and Stephen Halter noted that Unix sockets and named pipes have
  poor cross-platform ergonomics on Windows and still do not resolve QUIC/TLS
  constraints.

### Unified Rate Limiting and HTTP Error Code Standardization
* **Dual-Layer Rate Limiting Proposal:** Guest contributor Stephen Tyree
  introduced a draft SEP—inspired by Cliff Hall of FutureScale—addressing the
  lack of consistent rate-limiting guidance and machinery across MCP SDKs,
  clients, and servers. To support both stateless HTTP middleware and `stdio`
  servers, his design defines rate limiting across both the HTTP transport layer
  and a dedicated JSON-RPC error code, while reconciling unit differences
  between HTTP `Retry-After` headers (integer seconds or HTTP dates) and MCP's
  millisecond conventions.
* **Standardizing All HTTP Error Codes:** Kurtis Van Gent strongly endorsed the
  proposal and asked Stephen Tyree to expand it into a Transport Working Group
  SEP mapping every relevant HTTP status code to MCP schema responses and
  JSON-RPC error codes. Kurtis and Stephen Tyree cited widespread
  inconsistencies across SDKs and services—such as returning `HTTP 200 OK` with
  embedded errors versus transport-level status codes, or inventing incompatible
  JSON-RPC error numbers. Kurtis noted the SEP should align with previously
  reserved JSON-RPC error ranges and explicitly document any HTTP status codes
  intentionally omitted. Stephen Halter and Kryspin Ziemski agreed dual-layer
  error semantics remain vital even with HTTP over `stdio`, including for
  signaling costly or malformed query patterns to agents in financial
  market-data workloads.
* **External Vocabulary Registry Shelved:** Kryspin Ziemski floated creating a
  malleable, `schema.org`- or wiki-style external namespace referenced by the
  spec so contributors could extend shared vocabularies and error mappings
  without full spec revisions. Stephen Tyree argued that foundational SDK error
  handling must reside in the formal standard rather than *de facto* extensions,
  and Kurtis warned implementers would ignore guidance outside the spec. Kryspin
  concluded the concept fit better under discovery specifications like Agentic
  Resource Discovery (ARD) and withdrew the suggestion.
