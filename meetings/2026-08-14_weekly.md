# 2026-08-14 MCP: Transport Working Group (Weekly)

## TL;DR
The MCP Transport Working Group met to review the December 2026 specification
release timeline, vote on Sam Morrow's Internationalization Specification
Enhancement Proposal (SEP), and discuss Shaun Smith's Subscribe SEP addressing
inconsistent SDK subscription behaviors. Kurtis Van Gent outlined upcoming core
maintainer milestones—including an October 1 SEP lock list, an October 15 merge
deadline, and a mid-November freeze—while the group weighed a proposed
six-month release cadence against four-month cycles and overlapping SEP review
windows. The working group voted unanimously (three "accept" and three "accept
with changes," zero "decline") to advance the Internationalization SEP to the
core maintainers, conditional on adding concrete end-to-end examples that
cannot be solved via tool arguments and justifying why localization belongs in
the core specification rather than an extension. During that review, members
debated separating human-facing UI titles from model-facing tool descriptions
due to LLM tokenization differences, per-request tool mutation, and caching
impacts. Finally, the group examined inconsistent SDK behaviors where empty
subscription requests hold open idle Server-Sent Events (SSE) streams up to a
default 1,000-channel limit, debating whether to resolve the issue via explicit
specification language, a one-line rule closing empty streams, or failing
conformance tests.

## Detailed Summary

### Roadmap Schedule and Release Cadence
* **Roadmap Input and Working Group Continuity:** Sam Morrow and Kurtis Van Gent
  reviewed final working group inputs to the MCP roadmap ahead of Wednesday's
  core maintainer ratification, confirming that the Transport Working Group is
  continuing and that many items on its roadmap align with core maintainer
  themes.
* **December 2026 Release Milestones:** Following the July specification
  release, Kurtis explained that core maintainers are targeting a December 1–15
  release window. Key milestones include finalizing and publishing the roadmap
  around August 19–20, an October 1 SEP lock list (all SEPs must be open for
  review), an October 15 final deadline to merge SEPs, and a full specification
  freeze around November 15–17 so implementers have two weeks before release.
  With roughly two months until the October freeze, Kurtis emphasized
  prioritizing working group SEPs early to leave room for core maintainer
  feedback.
* **Release Cadence Trade-offs:** Kurtis shared a core maintainer proposal to
  standardize on a predictable six-month release schedule in June and December.
  Shaun Smith framed protocol scheduling as a "batch size problem" where large
  batches slow delivery and increase risk, though extensions help absorb rapid
  iteration. While Shaun personally preferred a four-month (thrice-yearly)
  cadence—such as two minor releases and one major release—he agreed six months
  is realistic given open-source maintainer consensus and SEP review cycles.
  Kurtis favored overlapping SEP windows so work does not stall during freezes,
  though both acknowledged the bottleneck that the same contributors author
  SEPs, review the specification, and write conformance tests.

### Internationalization SEP: Mechanics and Scope
* **HTTP Localization Standards and Automated Negotiation:** Sam Morrow
  presented an SEP formally adopting HTTP internationalization standards (such
  as `Accept-Language` headers) alongside `_meta` fields so implementations can
  leverage standard libraries with clear rules on translatable fields and
  caching. Sam cited multilingual public-sector and legal servers—such as
  Northern Ireland government documentation across three official languages—as
  key use cases. Kurtis Van Gent asked why tools could not simply take a
  `language` input parameter, noting the prior specification decision around
  sessions that protocol-level mechanisms must justify their complexity over
  in-context parameters. Sam explained that protocol-level negotiation enables
  automatic localization from a user's UI or terminal locale (including fallback
  preferences) and is essential during initial `tools/list` and resource listing
  calls before any tool arguments are passed so UI chrome and titles render in
  the user's language immediately.
* **User-Facing Interface Text vs. Model-Facing Content:** Shaun Smith and
  Kurtis Van Gent raised concerns about translating tool `description` fields
  based on `Accept-Language`. Shaun argued that protocol localization should
  target human-facing text (such as `title` annotations) rather than mutating
  what an LLM tokenizes, noting that languages tokenize very differently across
  models (such as dense Chinese tokenization in the DeepSeek tokenizer) and
  that cross-model prompt optimization is an LLM systems integration problem
  outside MCP's scope. Sam agreed tool `name` identifiers must never change and
  model-facing descriptions should not be translated by default, while resisting
  an outright ban when verbatim official translations carry legal weight. The
  group aligned on steering the SEP cleanly toward localizing human-facing UI
  text and cautioning that it is not intended for model-facing content, without
  strictly prohibiting server-specific content localization.
* **Audience Ambiguity and Cache Invalidation:** Kurtis noted that the boundary
  between user-facing and model-facing data is not always clear—pointing to CLI
  `/mcp list` commands exposing tool names, resources ranging from model-read
  skills to user-facing MCP apps, and structured versus unstructured tool
  outputs. Shaun pointed out that day-one audience annotations (`user` versus
  model) already exist deep in the content data model, despite low adoption.
  Shaun also warned that per-request `Accept-Language` changes mutate tool
  definitions and complicate caching; Sam noted that planned ETag caching work
  will complement this SEP by allowing clients to deterministically detect when
  a tool has changed underneath them and either re-list tools or fail closed.

### Internationalization SEP: Core Inclusion and Vote
* **Core Specification vs. Extension Justification:** Asked by Kurtis why
  internationalization should enter the core specification rather than starting
  as an extension, Sam argued that without protocol-level language negotiation,
  non-English server authors face a difficult trade-off between serving
  local-language users and maintaining broad reach across predominantly
  English-first agent environments. Sam pointed to early ecosystem
  demand—including GitHub's MCP server supporting custom JSON overrides for tool
  titles and descriptions, support on the roadmap draft for calling out HTTP
  localization goals, and global Agentic AI Foundation (AAIF) initiatives. Shaun
  agreed there is broad consensus behind localizing user-facing text.
* **Conditional Approval Vote:** Kurtis recommended advancing the SEP to core
  maintainers early to validate the overall approach, advising Sam to first add
  two or three concrete end-to-end examples that tool arguments cannot solve
  (including localizing server card titles and descriptions) and a clear pitch
  for why it belongs in core rather than an extension. In a show-of-hands vote,
  the proposal passed unanimously with three "accept" votes, three "accept with
  changes" votes (Kurtis Van Gent, Gabriel Zimmerman, and Shaun Smith), and zero
  "decline" votes.

### Resource Subscriptions SEP and SDK Discrepancies
* **Inconsistent SDK Defaults and Empty Subscriptions:** Shaun Smith introduced
  a Subscribe SEP (shared in Discord and via repository PR) addressing
  undesirable SDK behaviors when servers do not advertise subscribable
  resources or list-change notifications—features that participants noted see
  limited production adoption today. Using an LLM-assisted three-way analysis
  with verification test programs across the Python, TypeScript, and Go SDKs,
  Shaun found inconsistent defaults; notably, the TypeScript SDK lets clients
  send an empty subscription set while the server holds open an idle SSE stream
  with a default 1,000-channel limit, failing once that limit is exceeded.
* **Stream Exhaustion, Cluster Routing, and Extensibility:** Gabriel Zimmerman
  asked how clients determine whether list-change support is treated as a
  required capability during client-side filtering and whether subscription
  streams could use a separate URL from the main MCP server to mitigate
  persistent SSE stream exhaustion. Shaun confirmed that avoiding undesirable
  resource-consumption defaults on public-facing servers motivated the proposal,
  explaining that routing subscriptions to separate physical instances in a
  cluster is a backend routing concern handled via a shared-state backend rather
  than a separate protocol URL. Shaun also noted the specification needs a
  convention allowing extensions to declare new subscribable elements beyond the
  base protocol.
* **Specification Clarification vs. Conformance Testing:** Kurtis questioned
  whether the issue is a specification gap rather than an SDK implementation
  issue, noting servers can already omit subscription support or close streams
  at any time, and HTTP client SDKs should not open streams by default without
  an explicit call. Gabriel noted that HTTP `405 Method Not Allowed` already
  exists for unsupported features (which Sam previously tightened for `GET`
  streams on servers like GitHub's and Hugging Face's). Distinguishing HTTP
  status codes from JSON-RPC and standard I/O errors, Kurtis narrowed the gap
  to empty or non-intersecting subscription requests—proposing a one-line spec
  rule that servers return an empty acknowledgment and immediately close empty
  subscription streams rather than returning `404`. Sam suggested pairing a
  failing conformance test with minor language tightening (noting with Kurtis
  that even server discovery is technically optional for clients despite
  universal usage), while Shaun noted that SDK maintainers would reasonably
  expect explicit normative spec text behind any failing conformance test. Shaun
  agreed to re-investigate the specification before deciding between conformance
  tests and a text change.
