# 2026-10-02 MCP: Transport Working Group (Weekly)

## TL;DR
The MCP Transport Working Group reviewed a draft Specification Enhancement
Proposal (SEP) for primitive versioning alongside three architectural decision
documents aimed at aligning standard I/O (`stdio`) with Streamable HTTP. Shaun
Smith proposed extending cacheable list responses with an ETag-style `digest`
field, prompting debate over multi-list validation per request, list-level
versus per-primitive granularity, and rolling deployment churn; the group
agreed to independently update Section 5 of the caching specification so
Time-To-Live (TTL) values apply to full lists rather than individual pages, and
asked Shaun and Sam Morrow to document concrete user scenarios before
proceeding. On local transports, Kurtis Van Gent evaluated five alignment
options, with attendees reaching preliminary consensus on running HTTP/2 over
`stdio` (Option 1) rather than Unix domain sockets, LSP-style headers, or
HTTP/1.1. Participants also discussed preserving SDK-level transport interface
abstractions independently of specification-level pluggable transport proposals,
and debated introducing HTTP/2 over `stdio` via automated startup negotiation
versus an explicit `stdio_v2` transport. Formal votes on the `stdio` alignment
problem statement, HTTP/2 channel selection, and transition strategy were
scheduled for the start of next week's meeting.

## Detailed Summary

### Primitive Versioning Proposal and Expiry Semantics
* **Splitting the Caching and Versioning SEP:** Shaun Smith presented Part 1 of
  a split Specification Enhancement Proposal (SEP), divided from an earlier
  combined draft because MCP's JSON-RPC design lacks HTTP `GET` endpoints (such
  as for `tools/list` or `server/discover`) onto which HTTP ETags can directly
  map. Part 1 adds an optional `digest` field to the schema's `cacheable`
  result type for list queries (`tools/list`, `resources/list`, `prompts/list`,
  and extension list methods like skills, while excluding `resources/read`),
  deferring HTTP and server-card delivery bindings to Part 2. Shaun noted open
  questions around `server/discover` contents and guidance wording for
  `resources/read`.
* **Digest Replay and Validation Modes:** Working alongside existing advisory
  TTL hints, the `digest` field lets clients replay the version identifier they
  observed on subsequent requests. Participating servers can ignore incoming
  digests, serve the exact historical version requested, execute the request
  while returning an indicator that a newer version exists (allowing an agent
  to finish an active tool loop before refreshing), or return a staleness error
  requiring a refresh.
* **Naming and Version Retirement Trade-offs:** Gabriel Zimmerman asked why the
  field was named `digest` rather than `toolVersion` and whether an explicit
  retirement or expiry date should be added so clients can run automated tests
  before breaking tool updates take effect. Shaun explained `digest` stemmed
  from summarizing list contents via a hash algorithm and optional server salt,
  though both he and Kurtis Van Gent were open to renaming the field. Shaun and
  Kurtis opposed protocol-level expiry dates, warning they imply hard retention
  guarantees inconsistent with MCP's advisory hints and require complex
  calendaring logic; Kurtis favored ETag-style opaque IDs that let servers
  support layered versions concurrently while phasing out legacy tools.

### Digest Scope, List Granularity, and Deployment Churn
* **Single vs. Multi-Digest Request Validation:** Mark Roth questioned why a
  client making a targeted request (such as `tools/call`) could send digests
  from multiple unrelated list methods rather than only the relevant list's
  digest. Sam Morrow argued that cross-list validation enables servers to
  deterministically notify agents when broader session context—such as
  instructions, prompts, or newly added tools—becomes stale, especially during
  rolling deployments or rollbacks where short TTLs and long-lived listening
  streams (often drained last) fall short. Mark countered that if sending all
  digests is optional—or impossible when a client has not yet queried every
  list (e.g., `prompts/list`)—servers cannot reliably depend on it for coupled
  invalidation, whereas using a single server-wide digest would unnecessarily
  force clients to refetch unchanged lists.
* **Pagination and TTL Scope Discrepancy:** While comparing TTL and digest
  granularity, Shaun Smith highlighted that Section 5 of the current caching
  specification treats each paginated page as an independently cacheable
  response rather than scoping TTLs to the full list. Shaun, Mark Roth, and
  Kurtis Van Gent agreed that page-level TTLs should be updated independently so
  both TTLs and digests apply to an entire list.
* **Full-List vs. Per-Primitive Versioning:** Kurtis Van Gent raised concerns
  that list-level digests could cause excessive cache busting and context
  re-injection when only 1 of 100 tools changes, asking whether version IDs
  belong on individual primitives instead (citing long-lived agents resuming
  after multi-day hibernation). Shaun Smith and Mark Roth argued that per-tool
  versions only save bandwidth if MCP adds individual tool retrieval; Mark
  noted that even with a list-level digest, a server can track the latest list
  version at which each specific tool changed and honor calls to unchanged
  tools without forcing a `tools/list` refresh.
* **Rolling Deployments and Problem Statement Reset:** Sam Morrow and Mark Roth
  debated digest churn across mixed server instances during rollouts: Sam noted
  clients may fail closed or defer cache busting while servers monitor old IDs
  to drain traffic, whereas Mark advocated two-phase deployments that accept
  new digests before advertising them. Calling a 30-minute time check, Kurtis
  Van Gent asked Shaun Smith and Sam Morrow to step back and draft a brief
  problem statement with 4–5 concrete user journeys (including rolling deploys
  and hibernating agents) plus pros and cons for per-primitive versus
  list/group scope to align the group and establish clear user motivation for
  core maintainer SEP review.

### Aligning Standard I/O and Streamable HTTP Transports
* **Divergence Problem Statement and Core Requirements:** Kurtis Van Gent
  presented the first of three transport documents detailing discrepancies
  between `stdio` and Streamable HTTP, including request cancellation (JSON-RPC
  notifications vs. HTTP/1.1 connection closes or HTTP/2 stream resets),
  duplicated trace-context headers, concurrent request and notification
  handling, and future chunked streaming tool results. Kurtis defined six
  alignment requirements: running locally without opening network ports,
  preserving the `stdio` security model, reusing HTTP semantics across local
  and remote transports, supporting concurrent requests and server-initiated
  messages, defining startup failure/`stderr` and negotiation behavior, and
  keeping small-server implementation overhead manageable via SDKs.
* **HTTP/2 over Standard I/O vs. Header and HTTP/1.1 Alternatives:** Reviewing
  five local transport options in his second document, Kurtis noted preliminary
  alignment around *Option 1 (HTTP/2 over `stdio`)*, which keeps portless local
  execution and raises semantic parity with remote HTTP from roughly 70% to 90%
  (retaining minor framing differences like stream resets vs. connection
  closes) at the cost of requiring an HTTP/2 library; Kryspin Ziemski confirmed
  his TypeScript prototype already works across target runtimes. By contrast,
  *Option 2 (LSP-style headers over `stdio`)* solves header parity but lacks
  HTTP status codes and native streaming; *Option 3* leaves existing divergences
  unresolved; and *Option 5 (HTTP/1.1 over `stdio`)* was dismissed because a
  single `stdio` pipe cannot multiplex concurrent requests.
* **Unix Domain Sockets and Named Pipes Trade-offs:** Evaluating *Option 4
  (HTTP over Unix domain sockets or Windows named pipes)*, Mark Roth noted that
  Unix domain sockets reuse HTTP/1.1 clients and allow concurrent connections
  without network ports, suggesting file permissions could restrict access.
  Kurtis Van Gent countered that because clients spawn multiple `stdio` MCP
  servers under the same OS user, file permissions cannot stop one subprocess
  from messaging another's socket without client mediation. Kurtis and Kryspin
  Ziemski also cited OS socket path-length limits, uneven Windows Unix-socket
  support, and Docker socket-mounting complexity.
* **SDK Transport Abstractions and Maintainer Perspectives:** Attendees
  (including Kurtis, Kryspin, and Shaun Smith) agreed Option 1 is the preferred
  choice to vote on next week before engaging the SDK Working Group. Mark Roth,
  Kryspin, Kurtis, and Sam Morrow also discussed keeping an SDK transport
  interface abstraction: Mark noted HTTP/1.1 and HTTP/2 can share abstract HTTP
  semantics while differing at the lower layer, and Kryspin stressed TypeScript
  requires a transport interface for MCP Apps (`postMessage`) and aligns with
  meta-SDK plans in the SDK Working Group. Kurtis and Sam noted that while
  specification-level pluggable transports remain unlikely for the upcoming
  release due to core maintainer prioritization of universal client-server
  interoperability, there is strong maintainer support for aligning `stdio` with
  HTTP.

### Standard I/O Protocol Transition and Negotiation
* **Startup Negotiation vs. Explicit `stdio_v2` Transport:** In his third
  document, Kurtis Van Gent contrasted two rollout strategies for HTTP/2 over
  `stdio`. *Option 1 (Startup Protocol Negotiation)* negotiates support
  automatically at startup so package auto-updates (such as `uvx` or `npx`
  `@latest`) do not break user configs—a priority Sam Morrow emphasized major
  clients serving non-technical users will demand—but risks multi-layered
  handshakes and up to two process restarts against legacy servers. *Option 2
  (Explicit New Transport)* introduces a distinct `stdio_v2` configuration,
  providing production bake time ahead of MCP's 12-month deprecation window for
  legacy `stdio`; Kryspin Ziemski favored Option 2 with a grace period to
  create clear migration incentives over opaque startup probing.
* **Bidirectional Handshaking and File Descriptor Handoff:** Mark Roth favored
  startup negotiation to avoid forcing manual user migrations, initially
  proposing a JSON-RPC probe request before Kurtis Van Gent noted negotiation
  must be bidirectional across wire-incompatible protocols—suggesting a client
  environment variable paired with an initial server signal. Mark identified a
  key implementation question requiring investigation: how cleanly SDKs can run
  a startup handshake on `stdin`/`stdout` and then hand the open file
  descriptors to an HTTP/2 library.
* **Fallback Timeouts and Handshake Creep:** Kurtis Van Gent worried about
  repeating the friction of stateful/stateless HTTP negotiation and
  accumulating sequential handshakes across future protocol versions, though
  Mark Roth noted future negotiations can use native HTTP mechanisms once on
  HTTP/2. Sam Morrow proposed that clients set an environment variable, wait
  briefly for an HTTP/2 response, and fall back to legacy `stdio` `initialize`
  if none arrives (noting that major client hosts will likely prefer automatic
  fallback over breaking existing user configurations), while Kurtis flagged
  wait-timeout selection as a key risk.
