# 2026-07-24 MCP: Transport Working Group (Weekly)

## TL;DR
The MCP Transport Working Group reviewed a draft six-month roadmap covering six
active working tracks—tool versioning, pluggable transports, standard I/O
(`stdio`) evolution, streaming, internationalization, and tool
capabilities—plus sessions as a shelved honorable mention. The group aligned
on stack-ranking problem statements, assigning track owners, and securing core
maintainer buy-in in principle over the next two weeks before investing further
effort into individual Specification Enhancement Proposals (SEPs), deferring
votes on ready PRs such as internationalization in the interim. Members agreed
to pursue an MCP-specific ETag/digest mechanism for tool versioning, rule out
global-scope tool capabilities in favor of MCP's stateless model, and pause
active core protocol session work while extensions and stateless handle patterns
mature. Key technical debates centered on separating abstract protocol and
authentication semantics from transport-specific bindings (such as OAuth over
HTTP), addressing transport-proliferation and interoperability concerns without
SDK forking, and evaluating HTTP/2 over `stdio` pipes alongside gRPC and
other pluggable transports. With Kurtis Van Gent and Sam Morrow out next Friday,
Mark Roth will facilitate the upcoming meeting to review the updated roadmap PR
and conduct a formal working group ratification vote.

## Detailed Summary

### Roadmap Strategy, Ownership, and Meeting Logistics
* **Six-Month Roadmap and Maintainer Alignment:** Kurtis Van Gent presented a
  draft six-month roadmap PR modeled after the working-track structure from six
  months prior, outlining seven stack-ranked items with the goal of advancing
  roughly six tracks. Kurtis emphasized aligning on problem statements first and
  securing core maintainer buy-in over the next two weeks before investing
  heavily in detailed proposals. Consequently, Kurtis and Sam Morrow agreed to
  defer voting on Sam's internationalization PR until roadmap discussions
  conclude, and Shaun Smith noted that August will likely bring a
  three-to-four-week review lull.
* **Track Ownership Model:** At Mark Roth's suggestion, the group agreed to
  assign formal owners to each roadmap track, while aligning with Kurtis that
  tracks do not require a strict one-to-one mapping to Specification Enhancement
  Proposals (SEPs). Initial ownership includes Shaun Smith and Sam Morrow on
  tool versioning, Kurtis Van Gent and Mark Roth on pluggable transports, Shaun
  Smith on streaming, Sam Morrow on internationalization, and Gabriel Zimmerman
  on tool capabilities, while `stdio` evolution remains open unless folded into
  pluggable transports (with Kurtis offering to assist if needed).
* **Upcoming Meeting Facilitation and Scope:** Because Kurtis Van Gent and Sam
  Morrow will be unavailable next Friday, Mark Roth volunteered to facilitate
  next week's session. Although Gabriel Zimmerman offered to review his small
  tool capabilities SEP next week, Mark and Kurtis kept the scope focused on
  reviewing Kurtis's revised roadmap PR and holding a formal ratification vote
  before investing more effort in specific SEPs ahead of maintainer approval.

### Tool Versioning and List Digest ETags
* **Addressing Live Tool Rollout Gaps:** Kurtis Van Gent introduced tool
  versioning as the top-priority carryover item from the prior cycle, noting
  that while cache TTLs landed, MCP still lacks an ETag-like mechanism. Today,
  when a server updates its tools, clients remain unaware until they issue a new
  `tools.list` request. Kurtis outlined an optional version hash or UID per tool
  that clients pass back on tool calls, enabling servers either to route to the
  requested version or reject stale calls and prompt a `tools.list` refresh.
* **Why Standard HTTP ETags Do Not Map Directly:** Mark Roth asked whether
  replacing or eliminating the `stdio` transport first would allow MCP to rely
  directly on standard HTTP ETags. Kurtis explained that HTTP ETags are tied to
  HTTP resource retrieval semantics and do not transfer one-to-one because MCP
  relies on JSON-RPC and must carry version assertions inline within a single
  tool-call request.
* **Unifying List Digests and Tool Versioning:** Shaun Smith and Sam Morrow
  reported that their ETag proposal using digests on primitive list responses is
  nearly ready for submission. Sam expressed confidence that list-response
  digests work down to individual tools and proposed combining general list
  ETags and individual tool versioning into a single track to avoid redundant
  mechanisms, which Kurtis supported. Gabriel Zimmerman added that some clients
  may want explicit semantics to invoke or handle older tool versions rather
  than always throwing an error and refreshing immediately, committing to add
  this nuance on the PR.

### Pluggable Transports and SDK Architecture
* **Prioritizing Pluggable Transports and SDK Hooks:** Kurtis Van Gent and Mark
  Roth designated pluggable transports—supporting transports such as gRPC and
  WebSockets without SDK forking—as a top priority after missing the previous
  cycle. Mark and Pawan Bhardwaj noted that Python SDK v2 refactoring for the
  July release (including MRTR support) added experimental hooks amenable to
  pluggable transports, though Pawan highlighted open questions around idiomatic
  cross-language APIs and how much freedom versus restriction to impose on
  transport implementations. Sam Morrow also suggested defining a generic
  protocol envelope so metadata currently mirrored into HTTP headers maps
  consistently across transports and proxies cleanly.
* **Separating Protocol Semantics from Transport Bindings:** Kryspin Ziemski and
  Luca Chang noted that SDKs like TypeScript still bake JSON-RPC shapes directly
  into their transport/protocol interfaces. Kryspin advocated for clean
  separation enabling end-to-end in-process client-to-server execution without a
  wire protocol—benefiting conformance testing and sandboxed MCP apps using
  `postMessage`—and offered to share his vendored TypeScript diff. Mark Roth
  clarified that the architectural boundary should separate abstract *protocol
  semantics* from *transport bindings* across both client and server, rather
  than framing it as server versus protocol.
* **Addressing Interoperability Concerns and Preventing Forks:** Kurtis Van Gent
  and Mark Roth discussed core maintainer concerns that transport proliferation
  could fragment universal client interoperability, raise non-SDK implementation
  barriers, and perpetuate split specifications (which Sam Morrow suggested
  addressing via a unified spec contextualized per transport). While Kryspin
  noted that some developers already maintain custom SDK forks, Mark emphasized
  that forking is not a viable path for gRPC, and Kurtis highlighted using
  official spec guardrails and clean Python/TypeScript reference implementations
  to prevent ecosystem fragmentation.

### Standard I/O Evolution and Authentication Layering
* **HTTP/2 Over Standard I/O vs. Local Port Bootstrapping:** Clarifying
  questions from Shaun Smith on transport layering, Kurtis Van Gent contrasted
  two options for evolving `stdio`: bootstrapping a local HTTP port and token
  over `stdio` (which faces pushback for opening ports) versus mapping HTTP/2
  directly over `stdio` pipes (for which initial feasibility prototypes exist).
  Running HTTP over `stdio` retains interprocess isolation without open ports
  while unifying delivery semantics and eliminating payload-to-header
  duplication.
* **Re-evaluating the Solution Space and gRPC Overlap:** Mark Roth recommended
  framing the roadmap track around the problem statement ("what to do about
  standard I/O") rather than prescribing HTTP over `stdio` upfront. Mark noted
  that because roughly 90% of gRPC's implementation complexity lies in the
  underlying HTTP/2 stack, openness to HTTP/2 over `stdio` could lower barriers
  and reopen the broader transport solution space. Kryspin Ziemski suggested
  `stdio`, SSH, and `postMessage` could become pipe variants under pluggable
  transports or rely on a default SDK wrapper so existing `stdio` servers are
  not broken.
* **Decoupling Authentication from HTTP OAuth:** Sam Morrow and Luca Chang
  warned that MCP's OAuth-based auth spec depends on URLs and web identity
  concepts that do not map cleanly onto local `stdio` pipes, forcing a choice
  between subordinating all transports to HTTP or decoupling auth. Mark Roth
  advocated defining abstract, transport-independent authentication semantics in
  the core protocol, providing an official OAuth mapping for HTTP, and requiring
  other transports to define their own auth bindings; Luca and Kurtis agreed to
  make this layering explicit in the PR.

### Streaming, Internationalization, Capabilities, and Sessions
* **Incremental Bidirectional Streaming:** Kurtis Van Gent outlined the
  streaming track to overcome full-payload JSON-RPC buffering on both sides,
  enabling chunked delivery of large database results, generated images, and
  long documents as well as reverse client-to-server streaming for large file
  uploads. Shaun Smith highlighted Hugging Face's strong interest, pointed to
  his multi-modal API corpus, and noted the need to align streaming with MCP
  apps, real-time handovers, and tasks. Sam Morrow cited server memory-pressure
  issues he filed over a year ago for large file-storage workloads, suggesting
  streaming might belong in the `resources` spec—which Kurtis noted continues to
  see ecosystem interest around skills and file-oriented workflows rather than
  facing removal.
* **Internationalization and Caching Risks:** Kurtis reviewed Sam Morrow's
  internationalization track allowing clients to request localized descriptions
  to address the protocol's English bias. Kurtis raised questions around how
  English tool names interact with localized conversations, while Mark Roth and
  Kurtis identified caching interactions across languages as the primary
  technical challenge.
* **Stateless Tool Capabilities:** Kurtis and Gabriel Zimmerman reviewed
  handling tools in `tools.list` that require client capabilities like
  elicitation when a client lacks or loses support between calls. Gabriel
  confirmed that because MCP is stateless, the group ruled out global-scope
  capability state, and his updated SEP is ready for review once the roadmap is
  approved.
* **Shelving Core Sessions and Distributed Tracing Extensions:** Kurtis and Sam
  Morrow agreed to shelve active core session work, letting recent stateless
  transport changes, state-handle guidance, and the extensions track bake until
  compelling use cases emerge. While Kryspin Ziemski argued session isolation
  (including nested sessions) matters for multi-conversation servers, MCP apps,
  and Agent-to-Agent (A2A) mapping—and Gabriel suggested passing context-ID
  handles as tool parameters—Sam proposed an agent distributed tracing
  extension to pass context vocabulary across protocols without stateful core
  sessions, an idea Kryspin endorsed.
