# 2026-10-09 MCP: Transport Working Group (Weekly)

## TL;DR
The MCP Transport Working Group formally voted to approve the HTTP over
standard I/O problem statement and aligned on adopting HTTP/2 over standard I/O
(proposal #59) as the local communication channel after reviewing multi-language
prototypes and comparing HTTP/2 against HTTP/3 and QUIC. The group then focused
on the pluggable transports Specification Enhancement Proposal (SEP, #58),
examining a three-stage plan to decouple the MCP data schema from JSON-RPC,
remove wire-level JSON-RPC requirements for custom transports, and standardize a
transport boundary across Tier 1 SDKs. Enterprise participants and
members of the AMQP Technical Committee highlighted strong production demand
for gRPC, mTLS, and AMQP integrations alongside baseline Streamable HTTP and
standard I/O support. While members broadly favored cleaner separation between
transport metadata and application payloads, they debated the impact of breaking
SDK transport API changes and potential conflicts with the proposed SDK
extensions middleware model (SEP-3371), agreeing to review and refine the
strawman SEP ahead of MCPCon North America.

## Detailed Summary

### Agenda Updates and HTTP over Standard I/O Problem Statement
* **Agenda Shift and Versioning Status:** Shaun Smith reported that he had
  addressed comments from Kurtis Van Gent and Mark Roth on the tool and
  primitive versioning proposal, while new comments from Gabriel Zimmerman
  remained open for discussion. Kurtis shifted the initial agenda focus to HTTP
  over standard I/O to hold formal votes on items discussed the prior week.
* **Problem Statement and Requirements Approval:** Kurtis recapped the
  functional discrepancies between standard I/O and Streamable HTTP, including
  request cancellation, metadata representation, duplicated fields across
  headers and message bodies, concurrent request handling, and duplicate design
  work for new features like streaming. The proposed requirements mandate
  running locally without opening a network port, preserving the existing
  standard I/O security model, reusing HTTP semantics, supporting concurrent
  requests and server-initiated messages, defining startup, shutdown, failure,
  and `stderr` lifecycle behavior, and staying practical for small servers and
  SDKs across languages. The problem statement passed with 6 yes votes out of 10
  attendees.

### HTTP/2 Channel Selection, Prototyping, and HTTP/3 Trade-offs
* **Evaluation of Communication Channels (#59):** The group reviewed proposal
  #59, which compared HTTP/1.0 and HTTP/1.1 over standard I/O, LSP-style
  headers, HTTP over Unix sockets or Windows named pipes, doing nothing, and
  HTTP/2 over standard I/O, ultimately recommending HTTP/2 over standard I/O.
  Stephen Halter noted that although HTTP/2 is much harder to implement from
  scratch, it is the only option satisfying concurrency requirements, and
  confirmed that C# and most major languages support redirecting native client
  and server HTTP stacks over standard I/O streams with minimal effort.
* **Multi-Language Runtime Prototypes:** Following up on prior prototyping
  tasks—including an earlier Python prototype by Kludex—Kryspin Ziemski
  confirmed that TypeScript HTTP/2 over standard I/O works across modern
  versions of Node.js, Deno, and Bun aside from an older Bun version issue.
  Kryspin also built a functional initial Rust prototype and agreed to refine
  and circulate it with Rust SDK maintainers for validation.
* **HTTP/2 vs. HTTP/3 and QUIC:** Addressing a question from Mirja Kühlewind on
  whether HTTP/3 was evaluated, Kurtis Van Gent and Stephen Halter explained
  that HTTP/2 multiplexes streams over a single connection—treating standard I/O
  directly as one stream without TCP—whereas HTTP/3 relies on QUIC, adding
  unnecessary transport overhead and native library complexity such as `MsQuic`
  in C#. Mirja agreed QUIC is unnecessary overhead when TCP is stripped away,
  while noting an IETF QUIC Working Group effort (QUIC-Mux) to provide a
  stripped-down QUIC multiplexing shim over arbitrary stream protocols. Kurtis
  agreed to document the rationale for choosing HTTP/2 over HTTP/3 and QUIC.
* **Channel Vote and Poll Process:** Proposal #59 passed with 5 yes votes from
  regular working group participants, while several newer attendees refrained
  from voting due to lacking prior context. Participants agreed to add an
  explicit "Abstain" option to future polls and clarify voting eligibility for
  sustained contributors.

### Pluggable Transports: Background and Three-Stage Proposal
* **Background and Ecosystem Trade-offs:** Kurtis Van Gent reviewed prior
  discussions around pluggable transports, noting the tension between keeping
  MCP's baseline surface area small to preserve client-server interoperability
  and supporting enterprise environments that require custom transports—similar
  to how deployments already accommodate diverse authentication mechanisms.
* **Three-Stage Proposal (#58):** Kurtis outlined a three-part approach: (1)
  separating the MCP data schema from JSON-RPC so moving metadata like
  `protocolVersion` and `clientInfo` out of `_meta` into headers does not cause
  schema loss or duplication; (2) relaxing custom transport rules so JSON-RPC
  bytes are not mandated on the wire; and (3) requiring Tier 1 SDKs to expose a
  standardized transport interface, replacing today's inconsistent SDK seams and
  enabling custom transports to reuse existing SDK conformance test suites.
* **Clean Split, Fallbacks, and Fragmentation Risks:** Drawing on IETF Transport
  Services (TAPS) architecture experience, Mirja Kühlewind endorsed a clean
  data-to-transport split as future-proof while emphasizing fallback logic and a
  mandatory baseline protocol set for internet interoperability. Addressing
  Gabriel Zimmerman's concern about ecosystem fragmentation across cloud
  providers, Kurtis argued divergence already occurs when current SDK
  constraints require custom rewrites for enterprise needs, while Kryspin
  Ziemski noted that providing a structured opt-out "exit valve" reduces
  pressure to create separate protocol variants while keeping Streamable HTTP
  as the universal baseline.

### Enterprise Use Cases, Protocol Portability, and SDK Baselines
* **Build-Time vs. Enterprise Runtime Workloads:** Presenting slides from
  Amsterdam, Kurtis contrasted single-developer build-time tools (such as local
  coding agents) with multi-user enterprise runtime frameworks (such as
  LangChain, ADK, and LlamaIndex) that must integrate with existing production
  stacks using mTLS, load-balancer-free gRPC, request-signing proxies, platform
  worker bindings, SSH, or in-memory test transports.
* **Industry Demand for gRPC and AMQP:** Kurtis cited internal gRPC requirements
  across large-scale production environments, alongside multi-transport
  precedents in OpenTelemetry and Matter. Stefan Moser and Matt Pavlovich
  highlighted cross-industry collaboration on the AMQP Technical Committee
  driven by enterprise latency, backpressure, and legacy messaging integration
  requirements.
* **Application Portability and Tier 1 SDK Baselines:** Answering Mirja
  Kühlewind and Ramjot Singh, Kurtis explained that custom transports like gRPC
  would ship as modular add-on packages plugged into standard SDKs alongside
  Streamable HTTP so applications can support or migrate across protocols
  without rewriting business logic. Kurtis and Matt clarified
  that an HTTP-only interface cannot accommodate non-HTTP transports like AMQP
  or distinct HTTP and mTLS lifecycles, while confirming Tier 1 SDK recognition
  still requires implementing both standard I/O and Streamable HTTP across
  client and server SDKs.

### SDK Breaking Changes, Data Models, and Middleware Layers
* **Breaking API Changes vs. Faking JSON-RPC:** Speaking as a C# SDK maintainer,
  Stephen Halter expressed concern that #58 prescribes rigid API shapes rather
  than capabilities, forcing breaking changes on existing SDKs. While noting
  quirks like mutable JSON-RPC `2.0` version fields, Stephen asked whether
  transports could simply translate headers into `_meta` to mimic JSON-RPC.
  Kurtis countered that SDKs like TypeScript validate wire bytes directly
  against the spec's JSON-RPC schema, meaning moving fields out of `_meta`
  causes breakage regardless unless the data schema and transport seam are
  explicitly separated.
* **Comprehensive Payload Model and AMQP Binding Lessons:** Matt Pavlovich
  advocated packaging payload, metadata, and protocol version together so
  transports act as "dumb pipes," simplifying Unix CLI piping and file-based
  debugging while using reserved header/metadata namespaces to avoid vendor
  collisions. Stefan Moser added that the AMQP Technical Committee is opening an
  MCP-over-AMQP binding specification for public review and struggled with
  extracting fields from JSON-RPC, reinforcing the value of a common high-level
  SDK transport interface across client libraries.
* **Extensions SEP-3371 Middleware Conflict and Migration:** Kryspin Ziemski
  and Stephen Halter noted tension with the proposed SDK extensions SEP-3371,
  which defines separate transport and JSON-RPC middleware layers already used
  in C# for selective logging, ASP.NET Core authorization checks, and standard
  I/O-to-HTTP proxies. Shaun Smith and Mirja Kühlewind argued that intercepting
  raw JSON-RPC conflates transport metadata with application payloads and
  signals a need for cleaner logging and metadata abstractions. Kurtis noted his
  proposal exempts major-version SDKs until their next major release and
  suggested running legacy JSON-RPC and new transport abstractions in parallel
  during deprecation, which Stephen agreed would be a workable C# migration
  path.
