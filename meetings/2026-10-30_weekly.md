# 2026-10-30 MCP: Transport Working Group (Weekly)

## TL;DR
The MCP Transport Working Group reviewed updates to the tool primitive
versioning Specification Enhancement Proposal (SEP), discussed pagination cache
keys, evaluated HTTP over standard I/O (stdio) prototyping and handshake edge
cases, and examined subscription token lifetime enforcement in PR #67. For
primitive versioning and caching, the group aligned on keeping digest tags at
the list result level rather than per-tool, requiring clients to transmit all
known tags on requests, adding cluster consistency warnings for multi-node
deployments, and removing page numbers from paginated cache keys. During the
HTTP over stdio review, members shared prototyping progress across TypeScript,
Go, and Java and debated how to handle slow-starting or non-compliant legacy
servers that trigger silent discovery fallbacks, considering an optional
environment variable override for timeout edge cases. Finally, the group debated
strict protocol mandates versus application flexibility for OAuth token
expiration and revocation on long-lived subscription streams. Participants
agreed to keep server token enforcement non-prescriptive to accommodate
horizontally scaled architectures while introducing standardized
authorization-change error codes so clients know when to reauthorize and reopen
streams.

## Detailed Summary

### Tool Primitive Versioning and Caching SEPs
* **Optimistic List Caching Overview:** Shaun Smith walked through updates to
  the tool primitive versioning SEP following initial feedback from core
  maintainers at AGNTCon. The proposal extends MCP's `CacheableResult` type
  (alongside existing `ttlMs` and cache scope fields) with a digest/tag field
  for tool, prompt, and resource lists, reports stale tags in `_meta`, and adds
  a dedicated staleness error message.
* **Cluster Consistency and Continuous Deployment:** Gabriel Zimmerman raised
  concerns that rolling out updated tool lists to individual nodes in a
  multi-instance MCP server cluster creates inconsistent state, causing clients
  to discover a tool on one instance and fail execution on another. While
  versioning supports continuous deployment to targeted cohorts—allowing clients
  to re-index large toolsets or evaluate whether updated descriptions overlap
  with existing tools—both Gabriel and Shaun agreed this assumes cluster-wide
  consistency. Shaun committed to adding a warning in the SEP advising server
  authors to maintain consistent versions across server clusters.
* **Client Tag Transmission Rules:** Shaun Smith, Mark Roth, and Ramjot Singh
  debated three options for how clients send known tags on requests (such as
  `tools/call` or `prompts/get`) to detect staleness: sending all known tags on
  every request, sending an arbitrary subset of tags, or sending only the tag
  matching the current operation. While Ramjot noted arbitrary subsets could let
  read-only clients periodically check selected tags, Mark and Shaun agreed that
  unspecified subsets create undefined, unpredictable behavior. Shaun proposed
  requiring clients to send all known tags to enable early cross-primitive
  staleness detection (such as coordinated changes to server instructions and
  tools), and Mark agreed pending a quick check of prior meeting notes.
* **List-Level vs. Tool-Level Versioning:** Shaun raised Kurtis Van Gent's
  preference for fine-grained, per-tool versioning (with stable tool identifiers
  decoupled from names) to avoid refetching lists of 9,000–10,000 tools when one
  tool changes. Gabriel asked whether clients could simply diff lists locally,
  while Mark Roth noted that per-tool tags paired with sending all tags on every
  request would bloat every transaction with thousands of tags. Mark suggested
  deferring fine-grained delta fetching (e.g., requesting tool changes since a
  prior list tag) until proven necessary, and the group aligned on keeping tags
  at the list result level to keep the SEP tightly scoped.
* **Pagination Cache Key Removal:** Reviewing the existing caching
  specification's pagination rules, Shaun pointed out that treating each page as
  independently cacheable and including page numbers in the TTL cache key is
  unnecessary because clients cache holistic list contents rather than
  individual pages. Mark Roth agreed that page-keyed caching was unnecessary,
  and Shaun will submit a companion SEP removing page numbers from paginated
  cache keys alongside the tag caching SEP.

### HTTP over Standard I/O Prototyping and Handshake
* **TypeScript and Go Prototyping:** Kryspin Ziemski reported progress on a
  TypeScript HTTP-over-stdio prototype targeting Node, Bun, and Deno (noting
  Deno remains uncertain and older runtime versions required engine support,
  while TypeScript's formalized custom transport abstraction made separation
  clean). Juexin Wang shared that contributors are also prototyping the
  HTTP-over-stdio channel proposal in Go within MCP Toolbox for Databases.
* **Alignment with Pluggable Transports:** Kryspin asked Mark Roth how
  demonstrating a viable HTTP-over-stdio transport relates to the broader
  pluggable transports effort. Mark noted that Kurtis Van Gent is coordinating
  how the two complementary proposals are framed and suggested revisiting the
  topic at a subsequent meeting, while Shaun noted constructive discussions on
  pluggable transports at AGNTCon last week.
* **Discovery-to-HTTP/2 Handshake:** Shaun Smith and Juexin Wang reviewed the
  proposed wire handshake designed to avoid restarting stdio subprocesses: the
  client calls `server/discover` over stdio to exchange supported versions,
  selects and confirms a target version with the server, and transitions the
  stdio channel to HTTP/2 traffic. Mark Roth endorsed this architectural
  direction for the protocol.

### HTTP over Standard I/O Timeout and Process Edge Cases
* **Silent Fallback on Discovery Timeouts:** Drawing on a prior Java SDK
  prototype built with Kurtis Van Gent, Luca Chang highlighted an edge case
  where both client and server support the new version (with backward
  compatibility), but a slow-starting server misses the initial discovery
  timeout and triggers a silent downgrade to legacy initialization-based MCP.
  Mark Roth argued that legacy servers ignoring unknown JSON-RPC requests
  instead of returning errors exhibit server bugs rather than a protocol flaw,
  though Shaun noted one server in a small test sample already showed this
  behavior and Mark agreed RPCs still require finite timeouts.
* **Environment Variable Fallback Override:** Noting ecosystem precedent for
  out-of-band feature flags, Kryspin Ziemski suggested a legacy/version flag via
  environment variables as a forcing function. While Mark Roth opposed
  requiring environment variables for normal version migration, both Mark and
  Shaun agreed an optional environment variable configuring default fallback
  behavior when discovery probing times out is a practical workaround for slow
  servers.
* **Process Startup Coupling and Daemon Topologies:** Responding to Shaun, Luca
  clarified that subprocess stream reassignment is synchronous and decoupled
  from JSON-RPC discovery timeouts. Kryspin also asked whether deployments ever
  attach directly to pre-existing OS-level stdio daemons rather than spawning a
  subprocess or a lightweight stdio stub that pipes to a background daemon.
  Shaun and Luca confirmed unspawned stdio reattachment is not a practical
  pattern and that stub-to-daemon pipes behave identically to standard stdio
  servers from the client's perspective. Luca agreed to document the timeout
  edge cases on the SEP.

### Subscription Token Lifetimes and Authorization Error Codes
* **Subscription Stream Expiry Proposal (PR #67):** Ramjot Singh reported
  splitting his prior authorization proposals into PRs #67–#70 and presented PR
  #67. Because SSE and subscription streams currently authenticate only at
  connection establishment and can remain open indefinitely after an OAuth token
  expires or is revoked by an identity provider (IdP), PR #67 proposed requiring
  servers to close streams upon static token expiry and check revocation lazily
  while emitting dedicated error codes.
* **Horizontally Scaled Infrastructure vs. Over-Specification:** Mark Roth and
  Shaun Smith cautioned against mandating strict stream closure in the protocol.
  Mark explained that horizontally scaled services avoid complex centralized
  token-tracking infrastructure by checking expiry or asynchronous IdP
  revocation lazily (e.g., every 15–60 minutes) or allowing open streams to
  continue based on application-specific security requirements.
* **Stream Data Sensitivity:** Shaun observed that notification streams (such as
  `tools/list_changed`) signal state changes rather than carrying resource
  payloads directly. Ramjot noted that resource subscriptions can still surface
  activity signals (such as user presence or message edits), while Shaun noted
  that underlying resource content is gated behind subsequent `resources/read`
  requests (which enforce HTTP 401/403 checks) and that clock skew is handled at
  lower transport layers.
* **Non-Prescriptive Guidance and Authorization Error Codes:** Mark Roth, Shaun
  Smith, and Ramjot Singh aligned on keeping server token enforcement
  non-prescriptive while adding a brief note under subscribe/notify that streams
  should take account of the supplied authorization token. PR #67 will introduce
  standardized authorization-change error codes and messages (citing token
  expiry and revocation as examples) so clients know to acquire a fresh token
  and open a new stream to resume listening, or handle standard 401/403 errors
  if access was permanently revoked.
