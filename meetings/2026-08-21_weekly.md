# 2026-08-21 MCP: Transport Working Group (Weekly)

## TL;DR
The MCP Transport Working Group reviewed core maintainer feedback on the
December 15 specification roadmap, narrowed its immediate specification
priorities, and formulated a dual-track strategy for pluggable transports. Based
on core maintainer priorities and holiday capacity constraints, the group placed
HTTP over standard I/O (`stdio`), tool versioning (`ETag`s and caching), and
internationalization (`Content-Language`) above the December 15 cut line while
moving tool-result streaming to a longer-term exploration track. Because core
maintainers raised protocol-bifurcation concerns and left pluggable transports
outside the initial priority areas, members discussed whether to phase
Specification Enhancement Proposals (SEPs), define a JSON-RPC-agnostic SDK
interface, or transcode through existing JSON-RPC SDK object models. Ultimately,
the group aligned on two parallel efforts ahead of the mid-September Core
Maintainers meeting: aligning internal transport abstractions across SDKs via
pull requests alongside a public Python SDK v2 gRPC proof of concept, and
compiling concrete enterprise and ecosystem use cases to present to core
maintainers.

## Detailed Summary

### Roadmap Review and December 15 Prioritization
* **Core Maintainer Feedback and Release Cut Line:** Kurtis Van Gent shared
  feedback from the core maintainers' review of the roadmap targeting the
  December 15 specification update. Maintainers felt the Transport Working Group
  list was too large given upcoming holidays and raised concerns about pluggable
  transports, leaving the track outside the prioritized themes. Kurtis explained
  that Specification Enhancement Proposals (SEPs) within core priority
  themes—agentic messaging primitives, HTTP transport unification, agent
  identity and enterprise security, improved primitives (structured tool
  results, result audience, and progressive discovery), and improved or
  auto-generatable SDKs—will receive expedited review, while outside SEPs face
  longer queues and a higher justification bar.
* **HTTP over Standard I/O Focus Group:** Despite low initial working group
  sign-ups, core maintainers expressed strong interest in HTTP over standard I/O
  (`stdio`) to unify MCP onto a single HTTP transport model. Kurtis proposed
  forming smaller focus groups to drive active proposals; Stephen Halter and
  Mark Roth volunteered to join Kurtis on HTTP over `stdio`, Kurtis offered to
  recruit an additional contributor, and Shaun Smith noted interest in following
  its progress without dedicating time. Mark observed that HTTP over `stdio`
  makes sense with HTTP/2, whereas HTTP/1.1 is unclear, and cautioned that
  requiring HTTP/2 on MCP servers adds substantial overhead to `stdio`, which is
  meant to remain dead simple. Responding to Stephen, Kurtis confirmed initial
  caching work will not depend on HTTP over `stdio`, though the group will
  evaluate the consequences of eventually retiring the `stdio` transport.
* **Tool Versioning, Caching, and Internationalization:** Kurtis checked on the
  tool versioning (`ETag`s and caching) SEP drafted by Sam Morrow. Shaun Smith
  reported that the proposal is essentially ready and committed to completing a
  final review pass and coordinating with Sam on Discord so the group can
  present and vote on it next week. Sam's internationalization
  (`Content-Language`) proposal was also noted as ready for review and placed
  above the December 15 cut line.
* **Streaming Scope and Deferred Items:** Streaming did not make the core
  maintainers' priority list for December 15. Shaun Smith supported developing
  streaming on a longer timeline—potentially prototyping approaches
  independently first—and asked to explicitly scope the roadmap item to
  streaming of tool results rather than classic content streaming. Kurtis noted
  open questions around how streaming over JSON-RPC should look and potential
  overlap with separate proposals for resumable large-file parameter uploads.
  Error standardization and tool capabilities were also placed below the urgent
  cut line, alongside a no-work confirmation that stateful sessions will not be
  reintroduced.

### Pluggable Transports Architecture and JSON-RPC Trade-offs
* **Protocol Bifurcation vs. Wire Format Concerns:** Kryspin Ziemski proposed a
  phased approach that first aligns transport cut-point abstractions across SDKs
  before proposing wire-format extensibility, rather than leading with specific
  bindings such as gRPC. Kurtis Van Gent and Stephen Halter noted that core
  maintainers' primary concern is not JSON-RPC itself, but avoiding transport
  proliferation and ecosystem bifurcation in favor of consistent HTTP semantics
  and headers. Mark Roth observed that if the underlying concern is supporting
  custom transports at the specification level, splitting an SEP into two phases
  would not address that concern on its own.
* **Transcoding Across Stateless SDK Interfaces:** Mark Roth noted that while he
  opposed JSON-RPC transcoding back in December, the July specification's move
  to a stateless protocol makes mapping between an SDK's internal JSON-RPC
  interface and native custom transports (such as gRPC with protobuf—not gRPC
  carrying JSON-RPC payloads, which Mark called a non-starter) mostly
  straightforward. Stephen Halter agreed, pointing out that most tier-1 SDK
  transport interfaces expose deserialized JSON-RPC object models rather than
  UTF-8 byte streams, which also helps proxies bridge non-gRPC traffic over
  gRPC. Mark noted that accepting a JSON-RPC-expressed transport API is a
  workable fallback, though implementations would likely live with that
  transcoding inefficiency permanently.
* **Wire Format Invariants and Legacy Request IDs:** Mark Roth and Kurtis Van
  Gent noted that phrasing requiring JSON-RPC "on the wire" is technically
  imprecise since TLS encryption already transforms bytes in transit; Mark
  suggested the practical invariant is a reversible encoding that reproduces
  identical JSON-RPC messages at both endpoints, though a formal wording
  clarification is optional. Mark also observed that after the July spec
  updates, the JSON-RPC request ID is unused in HTTP and exists solely as an
  artifact of `stdio`. Replacing `stdio` with HTTP over `stdio` could eliminate
  request IDs entirely, though Mark later warned that retiring `stdio` without
  an agreed transport interface could remove the de facto reason SDKs maintain a
  pluggable transport layer today.

### Parallel Execution: Direct SDK Alignment and Python gRPC PoC
* **SDK-Level Transport Interface Alignment:** Mark Roth and Kryspin Ziemski
  agreed that aligning internal transport abstractions within individual SDKs
  can proceed independently of a specification change (SEP). Kryspin clarified
  his research document never required an SEP; noting that TypeScript and Rust
  already expose clean cut points and C# is close, he committed to submitting
  alignment PRs across non-aligned tier-1 SDKs (excluding manual Swift work)
  within three weeks. Stephen Halter expressed interest in reviewing and likely
  merging a minimal PR for the C# SDK.
* **SDK Governance and Architectural Best Practices:** Pawan Bhardwaj cautioned
  that without an SEP or explicit SDK maintainer agreement, internal SDK
  transport APIs are not guaranteed to remain stable. To encourage long-term
  consistency across implementations, Kryspin and Pawan discussed coordinating
  with Felix Weinberger and the general SDK development track on codifying the
  separation of transport handling from server logic as a general SDK
  architectural best practice.
* **Python SDK v2 Modularity and Public gRPC Proof of Concept:** Pawan Bhardwaj
  clarified that Python SDK v2 introduces a clean, modular dispatcher separation
  that enables custom gRPC dispatching without modifying the core SDK. Pawan
  confirmed that end-to-end gRPC protobuf tool-call tests are already working on
  a separate GitHub branch. Mark Roth directed merging this code into the `main`
  branch and releasing it publicly as a proof of concept, alongside reviewing
  Kryspin's SDK API research to evaluate parity gaps across other languages.

### September Core Maintainers Review, Proxies, and Ecosystem Use Cases
* **Preparing Use Cases for the September Core Maintainers Meeting:** Mark Roth
  and Kurtis Van Gent agreed to pair SDK prototyping with a formal presentation
  of custom transport use cases at the mid-September Core Maintainers meeting
  (around September 15–18), where Kurtis expects to represent the working group.
  Kurtis emphasized documenting concrete engineering motivations—such as
  gRPC-only enterprise stacks that cannot pull in HTTP—rather than just listing
  forks, and Mark noted the value of having affected external stakeholders share
  their requirements directly with core maintainers.
* **Proxy Architectures and AWS SigV4:** Kurtis invited members to submit
  one-paragraph summaries of custom transport requirements, specifically asking
  Luca Chang whether AWS `SigV4` authentication would benefit from a shared
  transport interface over writing a custom proxy. Luca agreed to evaluate it,
  noting that while proxies are doable today, they are more difficult than
  necessary and exist primarily to interoperate with systems restricted to
  official MCP transports. Mark added that proxies are also used to aggregate
  multiple backend MCP servers behind a single frontend server, and Kryspin
  noted sandboxed runtimes such as Cloudflare Workers.
* **In-Page / Null Transports:** Kryspin Ziemski described running in-page MCP
  servers over an internal RPC message-passing system—effectively an in-process
  or "null" transport instead of Streamable HTTP—without requiring a separate
  browser-specific protocol while significantly reducing context usage. Because
  Kurtis wanted clearer details on how an in-page transport reduces context
  usage, Kryspin committed to writing an explanatory document and pointed Kurtis
  to the `RPC transports` section of his 2,000-plus-line SDK and fork research.
